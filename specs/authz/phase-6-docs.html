Phase 6 — Documentation

Document custom roles and scoped permissions in the product docs so users can discover, compose, and assign a scoped role without reading the design. Ships last, once the surfaces it describes (Phases 2, 4, 5) are live.

1. What needs documenting

The redesign adds one user-facing concept — a role whose permissions are scoped to specific resources or resource types — reachable from three surfaces (API, dashboard, CLI). The docs must explain the concept once and then show each surface.

TopicReader question it answers
Roles & permissions modelWhat is a role, a policy, a scoped permission entry? How do managed and custom roles differ? What can and can't a custom role do (walk-up is downward-only; managed roles are immutable)?
Permission entry referenceWhat are the fields (resource_type, resource_id, scope, verb set)? What does * mean, and how does scope= confine it?
RecipesThe index use-cases as copy-paste examples: per-app CI/CD token, app maintainer, contractor on one app, read-only fleet monitor.
AssignmentHow to attach a custom role to a team member, API token, or trust policy (the existing --role flows).

2. Where it lives

Product docs live in /docs (the docs website, MDX). Extend the existing access-control / RBAC area rather than starting a new tree.

  • Concept page — roles, policies, managed vs. custom, the scoped-permission model. Pull the before/after framing from the design's data-model section, minus the schema detail.
  • Reference page — the permission-entry fields and the CLI --permission grammar (verb:type:id[:scope=parent]), kept in lockstep with Phase 5.
  • Recipes / how-to — one short task per index use-case, each showing both the dashboard path and the nuon roles create invocation.

3. Generated docs to regenerate

The API reference and CLI command reference are generated, not hand-written — regenerate them so the new roles endpoints and nuon roles commands appear, rather than documenting them twice.
  • API reference — regenerates from the Phase 1/2 swagger annotations; confirm the roles endpoints render with request/response bodies.
  • docs/cli-commands.mdx — regenerates from the Phase 5 CLI; confirm nuon roles create/list/delete and the --permission flag appear.

4. Files (anticipated)

  • docs/<access-control-area>/*.mdx — concept, reference, and recipe pages (extend the existing RBAC section).
  • Generated API reference — regenerated from swagger.
  • docs/cli-commands.mdx — regenerated from the CLI.
  • Navigation/sidebar entry for the new pages.

5. Acceptance

  • A reader can go from “I want a token that only triggers one app's branch runs” to a working role using the docs alone, on both dashboard and CLI.
  • The permission-entry reference matches the CLI grammar and the API body exactly — no drift.
  • Generated API + CLI references include the roles endpoints/commands.
  • Managed-role immutability and downward-only walk-up are stated explicitly so users don't expect a child entry to escalate.

6. Review checkpoint

Confirm the docs sit inside the existing access-control section rec vs a new top-level section, and that recipes track the final index use-case list.
