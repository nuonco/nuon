Phase 5 — CLI updates

Move the CLI onto the nested routes so a resource-scoped API token / OIDC identity works, and add commands to manage custom roles.

1. Use nested routes

The CLI (bins/cli/) drives the Go SDK (sdks/nuon-go). Phase 1 deliberately shipped no swagger or SDK surface for its nested routes — they reuse the bare handlers, which keep their original org-tier operations — so this phase adds that surface before it can repoint anything.

Method: annotate every nested path with its own @ID/@Router via a thin wrapper handler that delegates to the bare handler (nested*.go in each service package), regenerate the spec and client, then repoint the CLI.

All 53 nested paths are annotated: workflows under both owner types (installs/ and apps/…/branches/), install runner-jobs and their logs, install terraform-workspaces, app-scoped component build logs, and install policy-reports. Two gotchas worth recording: a wrapper inherits the bare route's @Deprecated and its path params, and go-swagger rejects the whole spec if one path param is undeclared or names a placeholder the path lacks — a log-stream handler declares log_stream_id, which no nested path carries.

Workflow calls take an ancestor through nuon.WorkflowOwner: set, they use the nested route; zero, they keep the bare one. The ids were already in scope at the call sites — apps/branches.go was passing "" into the workflow TUI's install slot and discarding the app/branch pair it had just resolved.

Left org-tier on purpose. nuon installs workflows get|steps and the dashboard server's SSE handlers are addressed by workflow id alone, with no ancestor in scope. Scoping them to the selected install would 404 whenever the id belongs to a different install, so they keep the bare route until they take an ancestor of their own.

2. Custom-role commands

Extend the existing nuon role surface to create and manage custom roles, mirroring the Phase 2 roles API. Each --permission is a scoped permission entry (repeatable):

nuon roles create --title "app_web release manager" \
      --permission "read:app:app_web" \
      --permission "all:app_branch:*:scope=app_web"
nuon roles list
nuon roles delete <role_id>

# assignment is unchanged — custom roles are just assignable roles:
nuon orgs api-tokens create --role <role_id>
  • The --permission value parses as verb:resource_type:resource-or-*[:scope=<parent>]; read/all and comma-joined verb sets both accepted.
  • Follows the CLI's agent-facing conventions (--output agent|json, --read-only blocks create/delete).
  • Managed roles are read-only; delete/edit reject them with the standard CLI error surface.
  • Assignment rides the existing --role flag on api-tokens / trust policies / invites — no new assignment command.

  • docs/cli-commands.mdx — hand-maintained, not generated; deferred to Phase 6 with the rest of the docs.

4. Acceptance

  • Child-resource CLI commands work for a resource-scoped identity (not just org admins) once enforcement is on — for the calls that have an ancestor in scope; see the callout in §1 for the ones that keep the org-tier route.
  • nuon roles create/get/edit/delete round-trips against the API; created custom roles are assignable via --role, which the API already resolves as either a role type or a role id.
  • --read-only blocks role mutations; --output agent emits a single envelope; managed roles reject mutation.
  • Bare-route org-admin commands unchanged.
