Phase 5 — CLI updates

Move the CLI onto the nested routes so a resource-scoped API token / OIDC identity works, and add commands to manage custom roles.

1. Use nested routes

The CLI (bins/cli/) drives the Go SDK (sdks/nuon-go). After Phase 1 regenerates the SDK with nested operations, repoint the CLI service layer at the nested calls for child resources, threading the app/install id the command already resolves. Bare-route calls that only org admins run (org-level operations) can stay as-is.

Method: find CLI service calls to bare child operations; switch to the nested SDK operation, using the -a/--app / -i/--install context the command group already has.

2. Custom-role commands

Extend the existing nuon role surface to create and manage custom roles, mirroring the Phase 2 roles API. Each --permission is a scoped permission entry (repeatable):

nuon roles create --title "app_web release manager" \
      --permission "read:app:app_web" \
      --permission "all:app_branch:*:scope=app_web"
nuon roles list
nuon roles delete <role_id>

# assignment is unchanged — custom roles are just assignable roles:
nuon orgs api-tokens create --role <role_id>
  • The --permission value parses as verb:resource_type:resource-or-*[:scope=<parent>]; read/all and comma-joined verb sets both accepted.
  • Follows the CLI's agent-facing conventions (--output agent|json, --read-only blocks create/delete).
  • Managed roles are read-only; delete/edit reject them with the standard CLI error surface.
  • Assignment rides the existing --role flag on api-tokens / trust policies / invites — no new assignment command.

4. Acceptance

  • Child-resource CLI commands work for a resource-scoped identity (not just org admins) once enforcement is on.
  • nuon roles create/list/delete round-trips against the API; created custom roles are assignable via --role.
  • --read-only blocks role mutations; --output agent emits a single envelope; managed roles reject mutation.
  • Bare-route org-admin commands unchanged.
