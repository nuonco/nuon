Authz redesign

URL-derivable authorization for ctl-api. If every resource is reachable by a route whose path encodes its full ownership chain, a request can be authorized from the URL alone — no database lookup to reconstruct ancestry, no denormalized ancestry columns.

Branch ja/authz (fresh, off main) · reviewed phase-by-phase before implementation.

The thesis

Authorization needs one thing: the ownership chain of scope tiers for the target resource (org → app → install → …), so it can ask “does this account hold a permission on any link in that chain with sufficient access?” Today that chain is not in the URL for “bare” routes like /v1/components/builds/:build_id, so the middleware reconstructs it from the database.

If instead every resource is reachable by a nested route — /v1/apps/:app_id/components/:component_id/builds/:build_id — the chain is fully encoded in the path params, and authorization becomes a pure function of (route pattern, path params, account permissions).

Why custom roles — example use cases

Today the only access is org-wide: the managed roles (admin / read-only / runner) each cover everything in the org at read or all. Custom roles add the missing “just this resource” axis — a role whose policy carries permissions scoped to specific resources or resource types. The model stays role-based end to end: you compose a role, then assign it through the same team / API-token / trust-policy flows as any managed role. Data model — before & after

The assignment spine is unchanged: an account still holds roles through account_roles, and a role still has exactly one policy. The only structural change is on Policy: today it carries an hstore of org-wide permissions; after, it keeps that hstore untouched and gains an additive scoped_permissions JSONB column holding an array of scoped entries. “Custom roles” are just roles (Managed=false) whose policy uses that new column.

The one rule that keeps URL-only authz safe: scope every query by its ancestors

The URL is a claim, not a fact. /v1/apps/A/components/C authorizing on A is only sound if C genuinely belongs to A. The ancestor-scoping rule makes that claim true: every handler behind a nested route must scope its query by every ancestor id that appears in the path (WHERE id = C AND app_id = A), not just the leaf id.

Scope by every id the URL asserts, because authz may rely on any of them — if the path named both an app and an install (/apps/A/installs/I/…), the handler would have to confirm I ∈ A as well, or a grant on A could reach an install from another app. Under one-level nesting (the recommended route shape) the path names only the resource's immediate owner, so in practice that's the single ancestor to scope on; the chain's higher tiers carry no id in the URL and match only via wildcards.

This is not extra work — it folds into the read the handler already does — but it is a discipline. Phase 1 makes it enforceable by giving each resource the owner columns to scope on; Phase 3 audits that handlers do it.

Backwards compatibility

  • Existing routes are untouched. Bare routes keep working; they authorize at the org tier. Nested routes are additive.
  • Existing roles keep working. An org role grants org-wide permission; the org is the last Link in every chain, so the walk-up authorizes org-role holders exactly as today. Scoped access via custom roles is strictly additive.
  • Rollout is gated by ScopedPermissionsEnabled. Off = today's org-scoped behavior, byte-for-byte.

Phases

1API routes & schema
Nested routes for child resources that lack them; schema so every chain is explicit. Existing routes untouched; bare routes authorize org-scoped.
2Scoped permissions & custom roles
A scoped_permissions JSONB column on policies, folding, scope-aware walk-up, and the roles API for composing custom roles. The model stays role-based.
3Enforcement
Middleware authorizing from the URL; one code path that keeps org roles working; actionable debug logging. Gated by ScopedPermissionsEnabled.
4Dashboard updates
Repoint child-resource calls to nested routes; custom-role management UI.
5CLI updates
Repoint child-resource calls to nested routes; nuon roles custom-role commands.
6Documentation
Product docs for custom roles & scoped permissions: concept, permission-entry reference, per-use-case recipes; regenerated API & CLI references.
