Phase 4 — Dashboard updates

Move the dashboard onto the nested routes so a resource-scoped user can use the app end to end, and surface custom-role management in the UI.

1. Use nested routes for reads/writes

The SPA (services/dashboard-ui/client/) calls bare routes for some child resources (the flat /v1/components/…, /v1/workflows/… families). Under Phase 3 those authorize at the org tier, so a resource-scoped user would be denied. Switch the affected lib/ctl-api calls to the nested equivalents from Phase 1 so access follows the user's role.

Method: grep client/ for calls to the bare child routes; repoint each at the nested route, threading the app_id / install_id the page already has in context. The generated OpenAPI types (client/types/nuon-oapi-v3.d.ts) regenerate from Phase 1 and drive the call sites.

2. Custom-role management UI

Extend the existing role surface for the Phase 2 roles API, org-admin only:

  • The roles list distinguishes managed (read-only) from custom roles; custom roles show their scoped permission entries.
  • A create/edit-role modal: title, description, assignment contexts, and a repeatable permission-entry row (resource type, resource picker with app/install/branch or “all of type”, optional parent scope for wildcards, and a verb-set selector). Follows the dashboard-ui:form skill for the modal form.
  • Delete a custom role from the table; managed roles are not editable or deletable.
  • Assignment reuses the existing team / API-token / trust-policy role pickers — custom roles simply appear as assignable options.

Placement: the existing team/role management area under org settings — no new top-level surface.

3. Graceful degradation while the flag is off

With ScopedPermissionsEnabled off, managed-role holders (everyone today) still hit the nested routes fine (org tier authorizes), so repointing calls is safe to ship before enforcement is on. The custom-role UI can be gated to the same flag to avoid offering roles that don't yet take effect pre-rollout.

4. Files (anticipated)

  • services/dashboard-ui/client/lib/ctl-api/* — repointed calls + extended roles calls.
  • services/dashboard-ui/client/components/roles/* (or the existing team/roles components) — custom-role table rows + create/edit modal with permission-entry rows.
  • services/dashboard-ui/client/types/nuon-oapi-v3.d.ts — regenerated.
  • Org-settings wiring where roles already live (no new page).

5. Acceptance

  • Every child-resource page fetches via a nested route; no dashboard call relies on a bare child route for data a scoped user should see.
  • Org admin can create, view, edit, and delete custom roles from the UI, and assign them via the existing role pickers; managed roles are read-only.
  • With the flag off, no behavior change for existing users.

6. Review checkpoint

Confirm the custom-role UI scope (full CRUD vs list+create only for v1) and that it extends the existing roles area rather than adding a new surface.
