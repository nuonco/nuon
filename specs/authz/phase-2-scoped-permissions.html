Phase 2 — Scoped permissions & custom roles

Extend the existing role/policy model so a policy can carry permissions scoped to a single resource (or all resources of a type under a parent), and let org admins compose those into custom roles — the entire model stays role-based. This is the data model and the roles API; enforcement is Phase 3.

Design decision (settled). Access below the org tier is delivered by roles, exactly like today — permissions are always mediated by a role assigned through account_roles, never attached directly to an account. A “scoped permission” is a new kind of entry on a Policy; a “custom role” is a role whose policy carries such entries. Everything rides the existing assignment surface (team members, API tokens, OIDC trust policies, invites) for free.

1. Model — a JSONB column on policies

A Policy already carries permissions as (objectID → permission) pairs in its Permissions hstore, and a role has exactly one policy (Policy.RoleID, unique index on role_id). Leave that hstore untouched (org-tier permissions keep working byte-for-byte) and add an additive JSONB column for the richer, scoped entries:

// Level enumerates the resource kinds authz recognizes — the link types an
// ownership chain can contain, and the kinds a permission can target or scope to.
type Level string
const (
    LevelOrg       Level = "org"
    LevelApp       Level = "app"
    LevelInstall   Level = "install"
    LevelAppBranch Level = "app_branch"
    // delegable org-owned siblings (webhook, vcs_connection, slack_subscription)
    // are NOT in the enum yet — they join it when a route scopes to them.
)

type PermissionEntry struct {
    ResourceType Level                    // the kind of resource this permission is on
    ResourceID   string                   // canonical id, or "*" = all of ResourceType within (ScopeType, ScopeID)
    ScopeType    Level                    // OPTIONAL parent level a "*" wildcard is confined to; "" = org-wide
    ScopeID      string                   // OPTIONAL parent id, of ScopeType; "" = org-wide
    Permissions  []permissions.Permission // subset of {create, read, update, delete}; ["all"] = all four
}

type Policy struct {
    ...
    Permissions       pgtype.Hstore     `gorm:"type:hstore"`                 // UNCHANGED — org-tier, byte-for-byte
    ScopedPermissions []PermissionEntry  `gorm:"type:jsonb;serializer:json"` // NEW — scoped entries
}

The Level enum is the single list of resource kinds authz distinguishes. Phase 1 ensures each level the routes express is a distinct link in the ownership chain (notably app_branch, so branch access is separable from whole-app access); leaf kinds like component join the enum only if we decide to scope permissions directly to them (Phase 3 review item 3).

  • Additive JSONB column, no hstore conversion. There is no precedent in this codebase for converting an hstore column to JSONB, and it is risky (every reader/writer flips at once, plus an ALTER ... USING transform). Instead we follow the 102_webhooks_match playbook: add a new nullable JSONB column via AutoMigrate; existing rows get NULL/empty and behave exactly as before.
  • "*" in ResourceID means “every resource of this type,” tier-scoped by (ScopeType, ScopeID), never leaking across tiers — distinct from the permission-set "*" fallback.
  • Matching is on ScopeID alone (ids are globally unique and self-typing by prefix); ScopeType exists to resolve a name→id, validate the scope is a legal parent of ResourceType, and render the entry legibly.

2. Permission resolution — Account.AfterQuery

Both columns fold into the account's effective permissions, unchanged in spirit from today — roles are still the only source:

  • hstore keys → folded into AllPermissions exactly as today (org-tier grants).
  • Object entries (ResourceID concrete) → AllPermissions.Grant(resourceID, perms).
  • Wildcard entries (ResourceID == "*") → TypeGrants[orgID][resourceType] holds {scopeID, perms} (org-wide when scopeID == "").

Membership (HasOrg / Account.OrgIDs) is still driven by role assignment via account_roles — nothing changes there, because a custom role is assigned the same way as a managed one.

Shared-core change (as built): permissions.Set held one Permission per object (map[obj]Permission), so it could not carry a verb subset like {read, create}. It is now map[obj]Verbs (all = {create,read,update,delete}). Managed-role hstore policies fold into the same Set via Add, whose merge is now a union — subsuming the old “keep the stronger grant” special case. This is not scoped-only; it touches the shared permission core.
The wire format of this field must not change. Account.AllPermissions serializes as the account payload's permissions field. Emitting verb arrays there broke every already-released CLI, which has the old type compiled in — it fails during user initialization, so every command dies, not just this field: 
unable to get current user: json: cannot unmarshal array into Go struct
field AppAccount.permissions of type models.PermissionsPermission
So Set.MarshalJSON emits the pre-verb-set shape: one verb string per object. UnmarshalJSON accepts either that or a verb array. A complete set reports all; a subset cannot be represented there, so it reports its least-privileged verb rather than overstating the grant. Nothing reads this field to authorize — the server authorizes from the Go value, and per-resource detail lives on Policy.ScopedPermissions — so the lossiness costs nothing.

The field is tagged swaggertype:"object,string" (matching the sibling Permissions hstore field) so the generated definition stays {type: object, additionalProperties: {type: string}}. This also avoids a startup failure: a map of verb arrays generates a $ref nested inside additionalProperties.items, which openapi2conv.ToV3 cannot resolve — codegen aborts and ctl-api never comes up.
Lesson for later phases. Any change to an existing response shape is a compatibility decision about deployed clients, not an SDK-typing detail. Phases 4 and 5 both touch client-facing surfaces.

3. Walk-up primitive — authz.Authorize(perms, wildcards, chain, perm)

Given a resource's ownership chain (most-specific first) it allows the request if any link carries a sufficient permission — an object entry on that link's id, or a wildcard entry on that link's type whose scope matches (see §4). The org id is the last link in every chain, which is exactly how managed org-role holders keep working.

Phase 3 supplies the chain from the URL instead of from a DB lookup — that substitution is the entire redesign.

4. App-scoped wildcards

“All of this app's branches” (read on an app, all on its branches) is a case an org-wide wildcard can't express. The three naive options all fail:

Attempt (entry)Why it fails
all · app · app_webtoo broad — walk-up gives all on the app itself and every install/component under it, not just branches
all · app_branch · * (org-wide)too broad — covers branches in every app, not just app_web
all · app_branch · brn_1, brn_2, …doesn't cover branches created later; unmanageable

Model: a wildcard entry carries an optional ScopeID naming the parent it is confined to. A custom role “app_web release manager” is then exactly two entries on its policy:

read · app        · app_web              // scopeID ""      → reads flow down to all children
all  · app_branch · *   scope=app_web    // all, but only on branches under app_web

Walk-up change: when Authorize reaches a link of type T, a type-wildcard for T authorizes only if its ScopeID is empty (org-wide) or equals the id of some ancestor link already in the chain. For a request to /v1/apps/app_web/branches/brn_y/runs the chain is [app_branch:brn_y, app:app_web, org]; the scoped wildcard's scope=app_web matches the app link, so it authorizes — and only for branches under that app.

authz.Authorize already receives the full chain, so ancestor ids are in hand; the wildcards argument gains a scope id per entry (map[type][]{scopeID, perm}). This is the one structural change to the reused core — small, and it generalizes to any “all of parent P's children of type T” entry, not just branches.

5. Permission granularity — verbs, not capabilities

Entries carry a subset of the four verbs {create, read, update, delete}, not just read/all. This is nearly free: Permission already enumerates all four verbs, FromRequest already derives the verb per request, and CanPerform already matches a request's verb against the granted permission (val == all || val == perm). The only real work is the §2 Set generalization (one value → verb set per object) so a resource can carry, say, {read, create}. read and all remain as aliases ({read} and all four).

Caveat that bounds this: the HTTP verb is a lossy proxy for risk. Destructive operations are not all DELETE — many are POST, so they map to create: 
POST /v1/installs/:id/deprovision      → create
POST /v1/installs/:id/teardown         → create
POST /v1/installs/:id/forget           → create
POST /v1/installs/:id/components/:id/teardown → create
So a create permission authorizes deploys and deprovision/teardown/forget. Verb-set entries give read-vs-write granularity, not deploy-vs-destroy. Achieving the latter (“deploy but not destroy”) requires a capability taxonomy — labelling each route deploy/destroy/configure/read independent of its HTTP verb — which is a larger, separate design.
Recommendation: ship verb-set entries now (cheap, strictly more expressive than read/all, backwards compatible). Defer capability-level permissions; do not pretend verb-level delivers “safe subsets” of destructive actions.

6. Custom roles — the delivery vehicle

A custom role is an ordinary Role (Managed=false, RoleType=custom) whose single policy carries ScopedPermissions entries. It is created, assigned, and revoked through the existing roles machinery — there is no separate concept to learn or build.

Custom roles are addressed by id, not by role type. They all share RoleTypeCustom, so the type alone is ambiguous. Role.AssignmentIdentifier() returns the type for managed roles and the id for custom ones, and a shared findOrgRole accepts either — so AddAccountOrgRole / SetAccountOrgRole / ResolveAssignableRole keep working unchanged across team, service-account, API-token, and trust-policy flows. ResolveAssignableRole deliberately rejects the bare string "custom" so an ambiguous request fails loudly instead of picking an arbitrary role.
Known gap, deferred to Phase 4. The dashboard role pickers build their options from role.role_type (client/hooks/use-roles.ts), so every custom role collapses onto the value "custom": duplicates are unselectable, and submitting sends role_type: "custom", which the resolver rejects. useRoleTitles is keyed the same way, so custom roles collapse to one entry in the team table. Custom roles are therefore visible but unusable in the UI until the pickers switch to role ids. Five components share that hook: team invite, change role, service accounts, change service-account role, and OIDC trust policies.

Titles are unique within an org

A title is what every picker displays, so two roles sharing one are indistinguishable in a dropdown and collapse to a single entry in the team table's title lookup. Uniqueness is enforced twice:

  • Validation on create/update trims the title, requires it non-empty, and rejects one already held by any role in the org — managed included, since a custom role named “Admin” is equally confusing. Compared case-insensitively: “Release manager” and “release manager” do not read as different options.
  • A partial unique index on (org_id, title) closes the race between concurrent creates, scoped WHERE deleted_at = 0 AND role_type = 'custom'. Managed titles are left to the reconciler — including them would put existing production rows at the mercy of this index at migration time — and excluding soft-deleted rows lets a deleted role's title be reused.

Assignment is unchanged: account_roles via the existing team / API-token / trust-policy / invite flows, which already accept any role the org owns. The role management routes are bare /v1/roles and authorize at the org tier (org-admin) — managing who-can-access is an org-admin action.

Managed roles are immutable

The managed roles (org_admin, org_read_only, runner, and the deprecated set) are owned and kept in sync by the authz reconciler. They are the platform's guarantee of a consistent baseline, so the write endpoints above must refuse to touch them:

  • PATCH /v1/roles/:id and DELETE /v1/roles/:id reject any role with Managed=true (return a 4xx explaining managed roles cannot be edited or deleted). Only Managed=false custom roles are mutable.
  • POST /v1/roles always creates Managed=false; a request cannot set Managed=true to forge a managed role.
  • The reconciler remains the sole writer of managed roles — this API never competes with it.

This keeps the managed catalog fixed and reconciler-authoritative while custom roles are freely additive.

Guardrails (settled). Entries are bounded by the org — every id is resolved within it, so cross-org ids cannot be referenced. Entry count is capped at 100 per role in validation. Scope depth needs no cap: the only legal wildcard scope is an app parent (§4).

8. Acceptance

  • An org admin can create a custom role with scoped permission entries, assign it via the existing role-assignment flows, and delete it.
  • Managed-role immutability: PATCH/DELETE on a managed role (org_admin / org_read_only / runner) is refused with a clear 4xx; POST /v1/roles cannot create a Managed=true role; the reconciler stays the sole writer of managed roles.
  • A member holding a custom role sees the role's ScopedPermissions reflected in AllPermissions / TypeGrants after query; a member with only managed roles is byte-for-byte unchanged.
  • authz.Authorize unit tests cover: object entry hit, org-wide wildcard hit, org-tier hit, miss, and scoped wildcard (matches only when its scopeID is an ancestor in the chain — e.g. all·app_branch·* scope=app_web authorizes a branch under app_web but not under app_billing).
  • Verb-set permissions: an entry of {read, create} authorizes GET and POST on its resource but denies PATCH/DELETE; read and all aliases behave as {read} and all four verbs; managed-role hstore policies still authorize exactly as before through the generalized Set.
  • Wire compatibility: the account payload's permissions field still serializes as {"obj":"all"}, so an already-released CLI parses it unchanged; a Set survives a round trip through either that shape or a verb array.
  • Unique titles: creating or renaming onto a title already used in the org is refused (case- and whitespace-insensitive, managed titles included); a role keeps its own title on update; deleting a role frees its title.
  • No enforcement wired yet (Phase 3) — custom roles exist and resolve into permissions but don't change request outcomes until the middleware consumes the chain.

Covered by internal/pkg/authz/{authorize,permissions} unit tests and the internal/app/roles/service integration suite (INTEGRATION=true).

9. Decisions settled

  1. Additive JSONB column, no hstore conversion settled — and no numbered migration was needed at all.
  2. Custom roles are the sole sub-org access vehicle; all access is mediated by a role settled
  3. Managed-role immutability, org-bounded entries, 100-entry cap, unique titles settled
  4. Verb-set permissions ship now; capability taxonomy deferred settled
  5. The account permissions field keeps its legacy wire shape settled — released clients must keep working (§2).
