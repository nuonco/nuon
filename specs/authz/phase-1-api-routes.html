Phase 1 — API routes & schema

Make every non-deprecated resource reachable by a route whose path encodes its full ownership chain, so Phase 3 can authorize from the URL alone. Add nested routes where missing; add owner columns where a chain can't be enforced. Leave all existing routes in place.

Non-goal. No authorization logic changes here. No route removals. This phase only adds routes and columns and wires handlers to scope by ancestors.

1. The chain lives in the route pattern

Phase 3 maps a matched gin route pattern to an ordered chain of scope tiers. That is only possible if the pattern names each tier:

Route shapeChain
/v1/installs/:install_id/…[install, app, org]
/v1/apps/:app_id/…[app, org]
/v1/apps/:app_id/components/:component_id/…[component?, app, org]
/v1/orgs/current/webhooks/:webhook_id[webhook, org]
/v1/components/:component_id (bare)[org] only

The chain is structural — derived from the pattern, not the database. A route the map doesn't recognize resolves to [org] and requires org-scoped access. That is the safe, backwards-compatible default.

2. Bare routes stay, at the org tier

Existing flat routes are not changed and not removed. Under Phase 3 they authorize at [org]: an org-role holder can use them; a resource-scoped role cannot. This preserves every current integration while steering scoped access onto the nested routes.

~50 of the ~98 owned-child “lookup” routes are already @Deprecated. They need no new nesting — they keep working org-scoped and age out.

3. Which resources need new nested routes

Rule (the doc's contract, not a frozen list): a resource gets a nested route iff it is (a) owned by an app/install, (b) not @Deprecated, and (c) has only a flat route today. Most of today's bare surface is already @Deprecated (the bare /v1/components/:component_id/…, /v1/install-workflows/…, /v1/action-workflows/…, install /deploys/… families) — those get no new nesting and age out org-scoped. The non-deprecated survivors and their decided routes:

ResourceNested route (one level)Ancestor-scoping predicate
install workflow + steps / approvals/v1/installs/:install_id/workflows/:workflow_id/…owner_id = :install_id AND owner_type = 'installs'
app-branch workflow/v1/apps/:app_id/branches/:app_branch_id/workflows/…owner_id = :app_branch_id AND owner_type = 'app_branch'
runner-job (install)/v1/installs/:install_id/runner-jobs/:idpolymorphic join → see §4
log-stream logs (install)/v1/installs/:install_id/runner-jobs/:id/logs (+ /tail, /spans)via runner-job→install, then its log_stream_id
component-build + build logs/v1/apps/:app_id/components/:component_id/builds/:build_id (+ /logs)join through component_config_connections
terraform-workspace (install)/v1/installs/:install_id/terraform-workspaces/:id (+ states, lock/unlock)polymorphic join → see §4
policy-reportnested under installinstall_id = :install_id (existing column)
Access outcomes this secures. A role with read on an install reaches that install's runner-job logs (deploys, sandbox runs, action-workflow runs) and its terraform workspaces via walk-up. Install vs. app-branch workflows are split by owner_type, so neither leaks into the other.
Build-log asymmetry. A component_build serves many installs (its install link is a reverse has-many), so its runner-job logs cannot be attributed to a single install by a WHERE clause. Build logs are therefore reached via the app-scoped build route — an app-scoped role sees them; install-scoped access does not. This is deliberate, not a gap.

Leave bare / org-tier (no single natural parent, or operational): queue, signal, org-level runner-job listing, and every @Deprecated route. The final list is confirmed during this phase against the live route inventory.

Decided — route shape: one level. A child is nested directly under its nearest already-nested owner (/installs/:install_id/workflows/:workflow_id), not full-depth (/apps/:app_id/installs/:install_id/…). One level is enough for the chain because :install_id resolves its own app during the handler's ancestor-scoped query, and it keeps URLs short.

4. Schema: handlers scope by ancestors, no backfill

A nested handler must make the URL's ownership claim true by scoping its read to the path ancestor. The survivors split two ways:

  • Direct owner column — components.app_id, app_branches.app_id, policy_reports.install_id already exist; the handler adds AND <col> = :ancestor to its existing org-scoped query. No migration.
  • Polymorphic owner — runner_job, terraform_workspace, and workflow carry no scalar install_id; they link via owner_id/owner_type. We scope with a polymorphic predicate (the decided approach) rather than backfilling a column: resolve the owner to the install through the install-bearing owner tables.
-- terraform-workspace under :install_id
WHERE org_id = :org
  AND ( (owner_type='install_components' AND owner_id IN (SELECT id FROM install_components WHERE install_id=:install))
     OR (owner_type='install_sandboxes'  AND owner_id IN (SELECT id FROM install_sandboxes  WHERE install_id=:install)) )

-- runner-job under :install_id resolves across the install-bearing owner types:
--   install_deploys (join install_components.install_id), install_sandbox_runs, install_action_workflow_runs
One shared scoping helper. Install-scoped access to every polymorphic child funnels through the same install-bearing owner tables (install_components, install_sandboxes / install_sandbox_runs, install_action_workflow_runs, install_deploys→install_components). Implement one reusable “does this owner_id/owner_type belong to :install_id?” predicate, not bespoke SQL per handler.
No ancestry backfill migration. Authorization no longer reads ancestry from the row; the handler resolves it from the URL's ancestor id through the existing owner links.

5. The chain must distinguish app_branch from app

App-branch routes are already nested (/v1/apps/:app_id/branches/:app_branch_id/…), but the ownership chain they express is only [app, org] today — the branch id is in the URL but the chain doesn't treat the branch as its own link. That collapses “access to this branch” and “access to the whole app” into one level, which Phase 2 needs to keep separate.

So Phase 1 records app_branch as a distinct link in the chain: Phase 3's chain builder emits {app_branch, :app_branch_id} as the leaf, giving [app_branch, app, org]. This is the routing/chain-shape decision; the corresponding Level enum value lives with the data model in Phase 2. It's the pattern for any child that must be addressable independently of its parent — and it's why the workflow split above routes app-branch workflows under the branch (app chain) and install workflows under the install.

6. Files (anticipated)

  • services/ctl-api/internal/app/**/service/*.go — new nested handlers (thin wrappers reusing existing service methods, adding ancestor-scoped WHERE clauses).
  • Route registration in each domain's Register*Routes.
  • services/ctl-api/internal/app/<resource>.go — owner FK column where missing.
  • One migration adding any missing owner FK columns (not ancestry).
  • Swagger annotations on new routes; regenerated SDKs.

7. Acceptance

  • Every non-deprecated app/install-owned resource has a nested route whose pattern names its chain.
  • Each new nested handler scopes its primary query by the path's ancestor id(s); a mismatched leaf/owner pair returns 404, not another owner's resource.
  • All pre-existing routes respond identically to before.
  • SDKs regenerate cleanly.

8. Decisions settled

  1. One-level nesting — children nest under their nearest already-nested owner.
  2. Polymorphic predicate, no backfill — polymorphic children scope via the shared install-owner predicate rather than a new scalar column.
  3. Install logs via runner-jobs — install:read reads runner-job logs at /installs/:install_id/runner-jobs/:id/logs.
  4. Build logs are app-scoped, not install-scoped — a build serves many installs.
  5. Terraform workspaces are install-scoped — reachable under /installs/:install_id/terraform-workspaces.
  6. Leave bare: queue, signal, org-level runner-job listing, all @Deprecated routes.
