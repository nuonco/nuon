Phase 3 — Enforcement

Authorize each request from its URL: build the ownership chain from the matched route pattern + path params, then walk it with authz.Authorize. No DB lookup to resolve ancestry. Backwards compatible with today's org-scoped auth, gated by ScopedPermissionsEnabled, with debug logging that says exactly why a request was allowed or denied.

1. Chain from the route pattern

A single ordered table maps route-pattern prefixes to the tiers their path params name — no database read, no denormalized columns. 

chainFromPath(fullPath, params, orgID) -> []authz.Link

Rules (first match wins, most-specific prefix first):

Pattern contains Chain
:install_id [{install, id}, {app, ""}, {org, orgID}]
:app_id [{app, id}, {org, orgID}]
org-owned prefix (webhook / vcs / slack) [{type, id-or-""}, {org, orgID}]
otherwise (bare / unrecognized) [{org, orgID}]
  • id is the raw path param — no DB read. Name-or-id params still work: a name is just an id we don't recognize as a grant target, so it falls through to the org/app tier grants the same way (the handler's own query resolves name→row).
  • An app link inside an install chain carries an empty id ({app, ""}): the walk-up treats an empty-id link as “no object grant at this tier, but a type-wildcard here still authorizes.”
  • The org id comes from the org middleware context, as today.

2. The middleware, end to end

if global/public: next()
resolve org      (as today)
resolve account  (as today)
perm  := permissions.FromRequest(ctx)          // GET→read, POST→create, …
chain := chainFromPath(ctx.FullPath(), params, org.ID)

if !ScopedPermissionsEnabled:
    // legacy: org tier only
    if acct.AllPermissions.CanPerform(org.ID, perm) != nil: deny (permissionDeniedError)
    else: allow
else:
    err := authz.Authorize(acct.AllPermissions, acct.OrgTypeGrants(org.ID), chain, perm)
    if err == nil:              allow
    else if !acct.HasOrg(org.ID): deny "no access to org"   // not even a member
    else:                        deny (permissionDeniedError with resolved chain)
The org-role fast path is not special-cased. An org-role holder has CanPerform(org.ID, perm), and org is the last link in every chain, so authz.Authorize returns nil for them on every route. That is the backwards-compat guarantee, expressed as one code path rather than a branch.

3. Ancestor-scoped handler queries (the safety rule)

Enforcement authorizes the claim the URL makes. The handler must make the claim true by scoping its primary read to the ancestors in the path (see the ancestor-scoping rule). Phase 3 includes an audit of the newly-nested handlers to confirm each does this; a leaf fetched by id alone behind a nested route is a finding, not an acceptable pattern.

4. Debug logging

At debug level on every authorized request, and at info level on every denial, log structured fields:

Field Value
route, method, permission the matched pattern, verb, resolved permission
chain install:inl_… > app:* > org:org_…
decision allow / deny
authorized_by grant:install:inl_… / wildcard:app / role:org / none
account_id, org_id identity
missing (deny only) human phrasing: “needs read on install inl_…, its app, or the org”

The denial returned to the client stays the human-readable permissionDeniedError from current main; the log carries the full chain detail for operators.

6. Acceptance

  • ScopedPermissionsEnabled=false: behavior byte-identical to current main; existing authz integration tests pass unchanged.
  • =true: managed org-role holders reach every route; an account holding only a custom role with read·install·X can GET install-X nested routes and is denied on install-Y and on bare routes; a custom role with all·app·A reaches every install under A via install-nested routes; a non-member is denied “no access to org.”
  • chainFromPath table tests cover install / app / org-owned / bare / name-as-id.
  • Denials log the chain and the actionable missing line.
