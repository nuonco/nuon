Phase 3 — Enforcement

Authorize each request from its URL: build the ownership chain from the route's path params, then walk it with authz.Authorize. No DB lookup to resolve ancestry. Backwards compatible with today's org-scoped auth by construction rather than by feature flag, with structured logging that says exactly why a request was allowed or denied.

1. Chain from the path params

The chain is built from the params the matched route declares — no database read, no denormalized columns, no prefix table. Only the tiers that can hold a grant contribute a link. 

chainFromParams(param func(string) string, orgID string) -> []authz.Link
Params present Chain (most-specific first)
install_id + app_id [{install, id}, {app, appID}, {org, orgID}]
install_id only [{install, id}, {app, ""}, {org, orgID}]
app_branch_id + app_id [{app_branch, id}, {app, appID}, {org, orgID}]
app_id only [{app, id}, {org, orgID}]
anything else (collections, bare, unrecognized leaf ids) [{org, orgID}]
  • id is the raw path param — no DB read. Name-or-id params still work: a name is just an id we don't recognize as a grant target, so it falls through to the org/app tier grants the same way (the handler's own query resolves name→row).
  • As built, an app-nested route carries the real app id. This doc originally specified {app, ""} for every install chain, but several routes name both tiers (/v1/apps/:app_id/installs/…). Using the id when the URL has one is strictly better: app-scoped object grants work there too.
  • Unrecognized leaf params (component_id, workflow_id, step_id, runner_id, …) create no links. Those tiers have no grant target, so they authorize from their ancestors in the URL — which is exactly why §3 is load-bearing rather than hygienic.
  • The org link is appended unconditionally, outside the tier checks, so no future edit to them can drop it and deny every request at once. A test asserts every param combination ends in a non-empty org link.
An empty app link does not help app-scoped wildcards. A grant scoped to app A authorizes only if A appears among the chain's ancestors, and on a flat install route the app link's id is empty. Recovering the real app id would need the DB lookup this design exists to avoid. So app-scoped grants take effect only through genuinely app-nested URLs; the empty link is still worth keeping, but only so an org-wide app-typed wildcard can authorize.

2. The middleware, end to end

if global/public: next()
resolve org      (as today)
resolve account  (as today)
perm  := permissions.FromRequest(ctx)          // GET→read, POST→create, …
chain := chainFromParams(ctx.Param, org.ID)

authorizedBy, err := authz.Decide(acct.AllPermissions, acct.OrgTypeGrants(org.ID), chain, perm)
if err == nil:                allow  (log at debug)
else if !acct.HasOrg(org.ID): deny "no access to this organization"
else:                         deny (permissionDeniedError, unchanged wording)
The org-role fast path is not special-cased. An org-role holder has CanPerform(org.ID, perm), and org is the last link in every chain, so authz.Authorize returns nil for them on every route. That is the backwards-compat guarantee, expressed as one code path rather than a branch.

Two structural guarantees stand in for a rollout flag: the unconditional org link (§1), and skipping the object-grant check on empty-id links — CanPerform treats a "*" key as matching any object, so without the guard an empty app link could authorize everything.

Collection endpoints

A collection route has chain [{org, orgID}], so it is authorized by an org-tier grant and nothing else. Custom roles reach lists the same way the managed read-only role does: a permission entry naming the org. 

{"resource_type": "org", "resource_id": "<org_id>", "permissions": ["read"]}

That resolves to a concrete grant on the org id, lands in AllPermissions, and matches the org link that ends every chain. Write grants stay scoped to specific installs or apps on top of it — “read-all, write-scoped.” No filtering layer, no new mechanism.

This is explicitly not read-restriction. A custom role cannot hide installs from its holder, because the list endpoints return everything the org-tier read grant covers. Per-grant collection filtering remains deferred; if read-restriction becomes a requirement, that doc is a blocker rather than a follow-up.

Top-level routes being org-scoped is a deliberate design choice, not a gap. Deprecated flat aliases that still exist beside nested forms (/v1/workflows/:workflow_id, /v1/components/:component_id, /v1/app-branches) therefore authorize at the org tier. This is fail-closed: a custom-role holder is denied through them, never over-granted.

3. Ancestor-scoped handler queries (the safety rule)

Enforcement authorizes the claim the URL makes. The handler must make the claim true by scoping its primary read to the ancestors in the path (see the ancestor-scoping rule). A leaf fetched by id alone behind a nested route is a finding, not an acceptable pattern.

The audit found four such handlers. All are pre-existing — today's org-tier check already lets any org member reach them — but two were not scoped by org either, making them cross-tenant rather than merely cross-install:

Handler Was Fix
updateInstallConfig received installID and never used it; patched by config_id alone — cross-org write all three queries confined to {id, install_id, org_id}
deleteAppSecret deleted by secret_id alone — cross-org destructive scoped to {id, app_id, org_id}; 404 when nothing matched
GetAppConfigGraph / V2 passed a client-supplied config id to GetFullAppConfig, which looks up by id alone new requireAppConfigOwner guard before the helper call
The first two are exploitable on main today, independent of this branch. Neither query was scoped by org, so any account with a membership in any org and a known config_id or secret_id can patch an install config or delete an app secret belonging to a different tenant. Nothing about the authz redesign introduced this; the redesign only found it.

Both fixes are self-contained — two handlers, no shared helper, no migration — so they can be cherry-picked into a small PR against main rather than shipping on this branch's timeline. That decision is independent of Phase 4 and should not wait for the rest of the redesign to merge.
GetFullAppConfig itself was left alone. It has 22 callers and nearly all pass install.AppConfigID read off an already-scoped install, so the helper is fine — only client-supplied ids are exposed. Guarding the two handlers is the narrow, correct fix; changing the signature would have touched 22 call sites for no gain.

Most initial sweep hits were false positives that scope through helpers such as getInstallComponent(ctx, installID, componentID) or findInstallComponent(ctx, orgID, installID, componentID). Phase 1 had already solved the hardest case correctly: requireWorkflowOwner("installs", "install_id") guards the install- and branch-nested workflow subtrees at the group level, so the handlers shared with the flat route cannot be reached with a mismatched owner.

Left unfixed, deliberately. runner_get_app_config.go has the same client-supplied-id pattern but is a runner-token route that does not go through the org middleware — a different auth model, not guessed at here. Separately, get_install_sandbox_run.go's @Router claims /v1/installs/{install_id}/sandbox-runs/{run_id} while the route is registered at /v1/installs/sandbox-runs/:run_id with no install_id. The code is correctly org-scoped; the annotation is wrong, so the generated SDK and docs describe a path that does not exist.

4. Debug logging

At debug level on every authorized request, and at info level on every denial, log structured fields:

Field Value
route, method, permission the matched pattern, verb, resolved permission
chain install:inl_… > app:* > org:org_…
decision allow / deny
authorized_by grant:install:inl_… / wildcard:app / role:org / none
account_id, org_id identity
missing (deny only) human phrasing: “needs read on install inl_…, its app, or the org”

The denial returned to the client stays the human-readable permissionDeniedError from current main; the log carries the full chain detail for operators.

6. Acceptance

  • Backwards compatibility holds by construction, not by flag: for an account with no custom role the walk-up reduces to the legacy org-tier check (§2). No separate legacy code path exists to test.
  • An account holding only a custom role with read·install·X can GET install-X nested routes and is denied on install-Y; a custom role with all·app·A reaches every install under A via app-nested routes; a non-member is denied “no access to this organization.”
  • chainFromParams tests cover install / app-nested install / branch / app / collection / bare / name-as-id, plus the two invariants: every chain ends in a non-empty org link, and unrecognized leaf params contribute nothing.
  • Denials log the chain and the actionable missing line.

7. Decisions settled

  1. No feature toggle — the new path is a provable superset of the old one, and a flag would revoke deliberately granted access rather than restore a safe baseline.
  2. Empty-id app links authorize only org-wide app-typed wildcards, never app-scoped grants and never object grants.
  3. Top-level routes are org-scoped by design, including the deprecated flat aliases. Fail-closed, not a gap.
  4. Collection filtering is out of scope. Custom roles reach lists via an org-tier read entry; read-restriction is not delivered by this phase.
  5. Deny logs at info, allow at debug.

8. Carried into later phases

  • Phase 4 (dashboard): SetAccountOrgRole replaces an account's roles, so an account holds exactly one role per org and a custom role cannot be layered on top of managed read-only. A custom role must therefore carry its own org read entry to be usable — the role builder should include it by default rather than making authors remember it.
  • Phase 4: resolveResource requires org entries to name the org id literally; accepting "current" would smooth the request shape.
  • Phase 4: the role pickers still key options on role_type, so custom roles remain visible but unusable (carried over from Phase 2).
  • Candidate for a separate PR against main: the updateInstallConfig and deleteAppSecret cross-org fixes in §3, which address a live exposure on main and need not wait for the redesign.
  • Unscheduled: the runner-route and swagger-annotation findings in §3.
