Denormalized Ancestors for Resource-Grant Authorization

Give every grant-relevant child resource direct install_id / app_id columns, so authorization is always a single point query — replacing the polymorphic owner walk.

Status: In progress on ja/resource-grants-v2 · Fallback: ja/resource-grants (walk-based, frozen) · 2026-08-09

1. Context

The hierarchical resource-grants design (resource-grants.html) authorizes a grant-scoped account by resolving the resource named by a request into an ownership chain — [install, app, org] — and matching grants against any tier of it. Accounts holding org roles never take this path; they short-circuit on the org-wide permission check.

The first implementation (branch ja/resource-grants) resolved that chain at request time. An audit of the full public-API surface (480 routes) showed how that lands:

1.1 The two-group model

The audit reduces to a simple invariant the API should have:

Nested route (names an install/app in the path) → authorized by a grant on the resource or any ancestor.
Top-level route → org-level permission required.

Group C is the violation: five child types — workflows, runner jobs, queues, log streams, terraform workspaces — whose only detail routes are top-level (GET /v1/workflows/:workflow_id). Applying “top-level ⇒ org-level” to them would lock a grant-scoped account (e.g. an Install Manager with admin on one install) out of its own install’s workflows, jobs, and logs, because no nested alternatives exist. The walk was a shim that makes those routes behave as if they were nested, by re-deriving the parent per request.

1.2 Why a walk, not a lookup

Two deficits stack. The URL lacks the owner (forcing a lookup), and the schema also lacks it: these tables store only a pointer to their immediate owner, which is often another child:

log stream → owner: runner_job
runner_job → owner: install_deploy
install_deploy → install_component → install   ← finally a grantable tier

The proof that the schema is the culprit: policy_reports and components have the same bare-route shape but carry direct app_id/install_id columns — they resolve in one query and sit in Group B.

Both options materialize the same fact — every child must know its grantable ancestor — at different layers.

3. Design

3.1 Schema

Add nullable install_id and app_id columns (indexed, no FK constraints, matching sibling denormalized columns elsewhere) to:

  • install_workflows
  • runner_jobs
  • queues
  • log_streams
  • terraform_workspaces

NULL is meaningful, not unknown: both columns NULL ⇒ the row is an org-tier resource (e.g. a management-runner job). Its chain is [org], satisfiable only by org-wide permission. app_id set, install_id NULL ⇒ app-tier. Both set ⇒ install-tier.

3.2 Write-time population

Centralized, not per-call-site: creation resolves the ancestor from the row’s owner_type/owner_id when the new columns are not already set, short-circuiting through the owner’s own denormalized columns (a log stream created for a runner job copies the job’s install_id/app_id — one point read, no recursion in steady state). Centralizing prevents the drift failure mode where a future creation site forgets the columns.

3.3 Backfill

Batched, idempotent migration; one targeted UPDATE … FROM per (table, owner-type) pair, derived from a complete inventory of creation sites. Tables fill in topological order — parents before children that reference them (runner_jobs before log_streams/queues owned by jobs) — so child backfills can read parents’ fresh columns. Rows whose owners are org-tier legitimately stay NULL.

3.4 Authorization

Resource resolution for these five types becomes a single org-scoped point read of (install_id, app_id) → chain [install?, app?, org] — identical in shape and cost to the :install_id routes in Group B. No recursive walk exists on this branch. Runners keep their single bounded hop (runner → runner group, whose owner is directly an org or install). Group C collapses into Group B, and Group D is eliminated (terraform routes resolve via query param / body owner; triggers are org-level by design). The remaining taxonomy: route-classified or one lookup.

3.5 Relationship to ja/resource-grants (fallback)

This branch (ja/resource-grants-v2) shares no git ancestry with ja/resource-grants; the enforcement layer (grants API, chain authorization, org-middleware deferred path, startup route-coverage validation, filtered collections) is re-implemented here column-first. The branches are mutually exclusive alternatives:

  • ja/resource-grants — frozen; request-time polymorphic walk; no schema changes. Merge this if the denormalization approach fails.
  • ja/resource-grants-v2 — this design; schema carries the ancestors; resolvers are point reads.

Whichever merges, the other is discarded; fixes do not flow between them automatically.

3.6 Enabling option 2 later

  • Nested detail routes (/v1/installs/:install_id/workflows/:workflow_id) scope children to the claimed parent with WHERE install_id = ? — the column, not a join chain.
  • The write-time resolution helper is the single source of “who is your grantable ancestor”, reusable by any handler.
  • Bare routes can then be downgraded to org-level (no deletion, no client break for org-role accounts) once clients migrate.
