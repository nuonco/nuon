Hierarchical Resource Grants

Object-level RBAC for ctl-api — replacing coarse org roles with grants that scope down to a single app or install (and, later, component / install-component).

Status: Draft / planning · Owner: auth-scopes · Last updated after pressure-test pass.

1. Motivation

Today the org roles (org_admin, org_support, installer, runner) all resolve to the same policy: {<orgID>: "all"}. Authorization happens once, in the org middleware, as acct.AllPermissions.CanPerform(org.ID, methodPerm). The role type is effectively metadata — there is no way to say “read-only” or “only this app”.

The original ask was apps_read_only and installs_read_only role types. Investigation showed that a resource-type dimension (“all apps”) is a large change to the permission scheme, whereas scoping to a specific resource fits the existing model almost for free — the permission Set is already map[objectID]Permission with a "*" wildcard. This doc designs the specific-resource path.

3. The ownership tree

Every grantable resource has a static (or resolvable) parent chain terminating at the org. Authorization walks up this chain: a request is allowed if the requested resource or any ancestor carries a grant satisfying the verb.

org ├─ app chain: app → org <- grant target (initial) │ ├─ install chain: install → app → org <- grant target (initial) │ │ └─ install-component (deferred target) │ ├─ component (deferred target) │ └─ (secrets, actions, runbooks, builds, releases … inherit via app/install) └─ (runner, runner-group, vcs, webhook … org-owned; deferred targets)

Initial grant targets are org, app, install. Everything else inherits via walk-up until promoted to a target.

Deploys, builds, releases, sandboxes, cloud accounts, audit logs, notebooks are not grant targets — they inherit from their parent install/component/app via walk-up.

4. Grant-target set (initial scope)

TargetModelOwnership tierVerbs

Initial scope is the three-level spine org → app → install. All app-owned and install-owned children (components, secrets, actions, runbooks, builds, releases, install-components, cloud accounts, notebooks, audit logs) inherit via walk-up from their app or install.

Deferred targets (add later via the extensible chain builder):

  • component — leaf under app; chain [componentID, appID, orgID]. Deferred: enforceable, but adds the deepest-param middleware work (F2/F4) and its main personas are covered acceptably by app grants at first.
  • install-component — leaf under install. Deferred with the same rationale; would be keyed on InstallComponent.ID (ic_...), resolved from the URL's (install_id, app-component-id) pair via the composite (InstallID, ComponentID) key.
  • runner, runner-group (polymorphic owner), vcs-connection, webhook, installer — org-owned siblings.
  • Runbooks/actions — pending an execute verb (section 9).

6. Data model

One unified table, folded into AllPermissions alongside role policies.

ResourceGrant {
  ID
  OrgID         // org the grant lives in (drives membership/OrgIDs)
  AccountID
  ResourceType  // initial: "org" | "app" | "install"
                // deferred: "component" | "install-component" | "runner" | ...
  ResourceID    // canonical ID of the granted resource
  Permission    // "read" | "all"
}

In account.go AfterQuery: after merging role policies, loop grants — merge each as {ResourceID: Permission} into the Set, and append OrgID to OrgIDs so an otherwise org-less account can pass org resolution. Keys are distinct canonical IDs, so the Set.Add last-wins hazard does not apply between grants.

7. Authorization primitive: walk-up-the-chain

// most-specific → least-specific; allow if any link satisfies perm
func Authorize(acct, chain []string, perm) error {
  for _, id := range chain {
    if acct.AllPermissions.CanPerform(id, perm) == nil { return nil }
  }
  return NoAccess
}

Chain builders per resource type (all hops are indexed, org-scoped lookups):

  • org: [orgID]
  • app: [appID, orgID]
  • install: [installID, appID, orgID] (install row carries app_id)
  • component: [componentID, appID, orgID] — deferred
  • install-component: [installComponentID, installID, appID, orgID] — deferred

The org-admin case ({orgID: all}) is just the last link, so this unifies the existing org gate with the new grants.

Deepest-path-param chain (needed only for deferred leaf targets, F2). For the initial org/app/install scope, each middleware keys off its single group param (:app_id or :install_id). When component/install-component are promoted, the middleware must instead inspect the full matched route and key off the most specific resource param — e.g. under /v1/installs/:install_id/components/:component_id resolve the install-component and build [installComponentID, installID, appID, orgID]. Designing the builder to select by deepest param now keeps that promotion additive.

8. Enforcement wiring

8a. Org-gate rework only non-additive change

Resource authorization is folded into the existing org middleware rather than living in separate middlewares (see 8b for why). The whole feature is gated behind one flag, ResourceGrantsEnabled (internal.Config → env RESOURCE_GRANTS_ENABLED). When it is off, the gate behaves exactly as before. When on, org.go splits membership from authorization:

orgErr := acct.AllPermissions.CanPerform(org.ID, perm)
if orgErr == nil {
    cctx.SetOrgAuthorized(ctx, true)                  // org-wide grant/role: fast path
} else {
    if !acct.HasOrg(org.ID) { 403 }                   // not a member at all
    cctx.SetOrgAuthorized(ctx, false)                 // member via a narrow grant; defer
    if !isFilteredCollection(ctx) {
        authorizeResource(ctx, acct, org.ID, perm)    // resolve resource in path + walk up
    }
}

Fail-closed: a deferred request that names no grantable resource in its path (and is not a filtered collection) is denied. Preserves today's behavior on every non-resource route.

8b. Resource authorization lives in the org gate revised from per-group middlewares

Earlier drafts registered one middleware per path-parameterized group (/v1/apps/:app_id, /v1/installs/:install_id) after org in the config chain. That was collapsed into the org gate itself for two reasons: (1) a single flag (ResourceGrantsEnabled) then enables the entire feature, with no dependence on the externally-managed middleware-order config list; and (2) it closes a safety gap — a flag-on-but-middleware-not-wired state would otherwise leave object routes unprotected. The org gate now resolves the most specific resource named in the path (authorizeResource → resourceChain: install first, then app; name-or-id, org-scoped), builds the ownership chain, and calls authz.Authorize. Filtered collections (8c) are let through to their handlers. All of this lives in internal/middlewares/org/ (org.go, collections.go).

8c. Collection-endpoint grant-scope filtering added post-pressure-test (F1)

Walk-up authorizes a single addressed resource, but list endpoints return whole collections with no per-item check. For a genuinely narrow grant, gating the whole endpoint is wrong in both directions (deny-all hides the user's own resource; allow-all leaks siblings). Fix has two parts:

  • Gate: collection routes let deferred (OrgAuthorized=false) members through instead of failing closed.
  • Filter: the query gains a grant-derived WHERE — return a row only if its own id, its parent app_id, or its org_id appears in the caller's grant set. Implemented per list query (get_org_installs.go, get_app_installs.go, get_apps.go, get_org_components.go).

Callers with an org- or app-read grant covering the whole collection skip the filter (their ancestor grant matches every row). Only narrow grants pay for it. A shared helper should turn the caller's grants + resource type into the id/app/org filter sets so the logic isn't duplicated across handlers.

8d. Collection filter — reference implementation

Why grants, not the flattened Set. AllPermissions is map[string]Permission — opaque ids with no tier information, so it can't tell “this id is an app” from “this id is an install.” The filter needs tiers, so the account must also carry its raw grants. Load them alongside roles and expose them:

// internal/app/account.go
type Account struct {
    ...
    Roles          []Role
    Grants         []ResourceGrant // preload: Preload("Grants")
    AllPermissions permissions.Set // still used by the middleware walk-up
}

Shared helper — turns the caller's grants into per-tier id sets for a given verb. Lives in a small package (e.g. internal/pkg/authz/scope) so every list handler uses identical logic.

// internal/pkg/authz/scope/scope.go
type IDSets struct {
    OrgIDs     []string
    AppIDs     []string
    InstallIDs []string
}

// a grant satisfies the request if it is "all" or exactly the requested verb
func satisfies(g permissions.Permission, want permissions.Permission) bool {
    return g == permissions.PermissionAll || g == want
}

// ForList collects the resources the caller is granted at each tier for `perm`.
func ForList(acct *app.Account, perm permissions.Permission) IDSets {
    var s IDSets
    for _, g := range acct.Grants {
        if !satisfies(permissions.NewPermission(g.Permission), perm) {
            continue
        }
        switch g.ResourceType {
        case "org":     s.OrgIDs = append(s.OrgIDs, g.ResourceID)
        case "app":     s.AppIDs = append(s.AppIDs, g.ResourceID)
        case "install": s.InstallIDs = append(s.InstallIDs, g.ResourceID)
        }
    }
    return s
}

Per-resource GORM scopes. Each returns a func(*gorm.DB) *gorm.DB to drop into .Scopes(...). The row is visible if any tier it belongs to is granted. Empty IN ? slices compile to IN (NULL) (match nothing), so a caller with no relevant grant gets an empty list — not an error, which is the right behavior for a collection.

// installs list: columns installs.id, installs.app_id, installs.org_id
func (s IDSets) Installs(db *gorm.DB) func(*gorm.DB) *gorm.DB {
    return func(tx *gorm.DB) *gorm.DB {
        return tx.Where(
            db.Where("installs.id IN ?", s.InstallIDs).
                Or("installs.app_id IN ?", s.AppIDs).
                Or("installs.org_id IN ?", s.OrgIDs),
        )
    }
}

// apps list: columns apps.id, apps.org_id
// plus UPWARD visibility: show the parent app of any granted install/component
// so a narrow grantee can navigate to it (metadata only; its other children stay filtered).
func (s IDSets) Apps(db *gorm.DB) func(*gorm.DB) *gorm.DB {
    return func(tx *gorm.DB) *gorm.DB {
        return tx.Where(
            db.Where("apps.id IN ?", s.AppIDs).
                Or("apps.org_id IN ?", s.OrgIDs).
                Or("apps.id IN (?)",
                    db.Model(&app.Install{}).
                        Select("app_id").
                        Where("id IN ?", s.InstallIDs)),
        )
    }
}

Handler wiring — skip the filter entirely when the org gate already authorized org-wide; otherwise apply the scope. Example for get_org_installs.go:

func (s *service) GetOrgInstalls(ctx *gin.Context) {
    org, _ := cctx.OrgFromContext(ctx)
    acct, _ := cctx.AccountFromContext(ctx)

    tx := s.db.WithContext(ctx).
        Joins("JOIN apps ON apps.id = installs.app_id").
        Where("installs.org_id = ?", org.ID)

    if !cctx.OrgAuthorized(ctx) {                       // deferred member: narrow scope
        sets := scope.ForList(acct, permissions.PermissionRead)
        tx = tx.Scopes(sets.Installs(s.db))
    }
    // ... existing q / runner_id filters, ordering, pagination unchanged ...
}
Upward visibility — decided: navigable (§9). The Apps scope surfaces the parent app of a granted install so the grantee can see where their install lives, but that app's other installs remain filtered by the Installs scope. This keeps navigation coherent without leaking siblings. The strict-isolation variant (drop the subquery branch) is not used.
Endpoints to update (each gets the OrgAuthorized guard + its scope): get_org_installs.go, get_app_installs.go (already app-scoped — only needs the install narrowing when the caller lacks the app grant), get_apps.go, get_org_components.go. Note that since component is a deferred target, the components-list filter matches at the app_id/org_id tiers only (no component-id tier yet): an app·read grantee sees that app's components; an install·read grantee correctly sees none in the org-wide list (their scope is the install, reachable via /v1/installs/:id/components, not the org-wide component list). Any future list endpoint over a grantable resource must adopt the same pattern — consider a lint/review checklist item so new collections don't silently ship unfiltered.

8e. Query performance

The filter is cheap in the expected case but has a few sharp edges worth stating explicitly.

Why it stays cheap: the mandatory org predicate. Every list query already AND's an unconditional WHERE <table>.org_id = ? before the grant scope. Postgres uses the org_id index to narrow to a single org first, then evaluates the OR-of-INs over that already-small subset. An org's app/install count is bounded (hundreds, low thousands), so the OR filter runs in-memory over a narrow row set. The classic “OR across columns → seq scan” hazard can therefore only ever scan within one org, never the whole table. Note that for a narrow (deferred) grantee, OrgIDs is empty (an org grant would have taken the fast path), so the effective filter collapses to id IN (…) OR app_id IN (…) over the org-narrowed rows.

RiskImpactMitigation
OR-of-INs can't use a single composite index Planner bitmap-ORs separate index scans or filters post-narrowing. Negligible at org scale. Ensure each filtered column is independently indexed: org_id, app_id (present), id (PK). No new composite index needed.
High grant cardinality (e.g. 500+ install grants on one account) id IN (…) with a large literal list; fine to low thousands, degrades beyond. If grants-per-account grows large, swap the materialized IN lists for a JOIN against resource_grants (below). Not needed at expected scale.
Separate COUNT(*) for pagination totals Correctness, not just perf: an unfiltered count over-reports the page total. Apply the same .Scopes(...) to the count query. Audit each list handler's pagination path.
Upward-visibility subquery in the apps list One extra lookup apps.id IN (SELECT app_id FROM installs WHERE id IN (…)). Single indexed scan on installs.id → app_id; the outer query is already org-narrowed. Negligible.
Admin / org-wide callers No regression — the large-org unfiltered plan is unchanged. The OrgAuthorized fast path skips the filter entirely for them.

Scalable alternative (only if grant cardinality demands it): replace the Go-materialized IN lists with a JOIN, letting an index on resource_grants(account_id, resource_id) do the work and keeping grant volume off the query string:

JOIN resource_grants rg
  ON rg.account_id = @acctID
 AND rg.deleted_at IS NULL
 AND (
   (rg.resource_type = 'install' AND rg.resource_id = installs.id)      OR
   (rg.resource_type = 'app'     AND rg.resource_id = installs.app_id)  OR
   (rg.resource_type = 'org'     AND rg.resource_id = installs.org_id)
 )

The IN-list form is recommended initially for its simplicity; this JOIN form is the escape hatch if a single account ever accumulates thousands of grants. Both are org-narrowed first, so both are fast in practice.

Bottom line. With the org predicate always leading, the filter adds a cheap in-org OR-filter for narrow grantees and nothing at all for org/app-wide grantees. The only items that need active attention are (1) indexing the three filter columns and (2) applying the scope to any pagination COUNT query — the latter is a correctness bug if missed, not merely slow.

9a. Grant management API revised: unified surface

Rather than a grant sub-collection per resource (/v1/installs/:id/grants, /v1/apps/:id/grants, …), which would need a fresh triple of endpoints for every grantable tier, grants are managed through a single resource-agnostic surface. The resource is named in the request body (create) or query (list), not the path. This keeps the API flat as more tiers become grantable and makes the org tier — the “read everything in the org” grant — a first-class target with no extra endpoints.

MethodRouteNotes
POST/v1/grantsCreate/upsert. Body: { resource_type, resource_id, account_id|email, permission }. resource_type is oneof=org app install; permission is oneof=read all. Apps/installs accept name-or-id (resolved & validated against the caller org) or the "*" wildcard (see 9b); org must be the caller's own org. Org-admin only.
GET/v1/grantsList grants in the org; optional ?resource_type=&resource_id= filter.
DELETE/v1/grants/:grant_idRevoke. Org-admin only.

Org-wide read (read everything in the org) is a single org · read grant — it cascades to every app and install via walk-up authorization and is bucketed at the org tier by the §8d collection filter. An app · read grant similarly covers all installs under that app. For “all resources of one tier” (e.g. all installs but not apps), see the type-wildcard grant below.

9b. Type-wildcard grants supported

A grant whose resource_id is "*" scopes to every resource of its resource_type within the org — e.g. { resource_type: "install", resource_id: "*", permission: "all" } grants write on all installs in the org, and crucially not apps or other tiers (which org · all cannot express). Supported for app and install; org takes no wildcard (it is already a single resource).

The wildcard deliberately does not reuse the permissions.Set "*" key, which CanPerform falls back to for any object regardless of tier — using it would leak an install · * grant to apps and the org. Instead the tier is carried explicitly:

  • Aggregation (account.go AfterQuery): wildcard grants are collected into Account.TypeGrants map[string]permissions.Permission (keyed by resource type), separate from the flat AllPermissions Set.
  • Walk-up (authz.Authorize): the ownership chain is a []Link{Type, ID} (not bare ids); a link is authorized by a specific-object grant or a TypeGrants entry matching that link's tier. An install · * grant matches the install link but never the app or org link.
  • Collection filter (scope): IDSets gains AppWildcardOrgs/InstallWildcardOrgs; the list queries widen to org_id IN (…) for the wildcard tier (an app wildcard cascades to that org's installs and components; an install wildcard grants upward visibility of parent apps but not components, matching per-install grants).

Deferred (with the deferred targets)

  • Execute verb: runbooks/actions need an execute permission, not CRUD. Not in initial scope (those aren't initial targets), but the Permission enum and FromRequest mapping should be left extensible so adding execute later is additive.
  • Polymorphic owners: runner-group and workflow resolve their owner at runtime via OwnerID/OwnerType. When promoted, the chain builder must dispatch on OwnerType (introduce typed constants for it — today it's an untyped string). The deepest-param builder design already anticipates per-type resolution.

Findings & design changes

F1 — Collection endpoints need result-filtering (biggest gap). Walk-up authorizes a single addressed resource; list endpoints (GET /v1/installs, /v1/apps/:id/installs, /v1/apps, /v1/components) return everything in the org/app with no per-item check. A narrow-grant user is either denied the whole list (can't see their own install) or, if the gate is relaxed, sees everything (leak). Resolution: these endpoints must (a) let deferred accounts through the gate, and (b) add a WHERE derived from the grant set — return rows whose id, parent app_id, or org_id matches a granted resource. This is a real scope increase: each list query gets a grant-scope filter (design in §8c, reference implementation in §8d). Org- and app-read holders are unaffected (their grant covers the whole collection); only genuinely narrow grants need the filter.
deferred F2 — Deepest-path-param chain (for deferred leaf targets). Only relevant once component/install-component are promoted. In initial scope, /v1/installs/:install_id/components/:component_id is authorized by the install chain [install,app,org]. On promotion, the middleware must detect :component_id, resolve the InstallComponent by (install_id, component_id), key on InstallComponent.ID, and build [installComponentID, installID, appID, orgID]. Designing the builder to select by deepest param now makes that promotion additive.
F3 — Out-of-group routes need per-handler resolution. /v1/workflows/:workflow_id (and deprecated /v1/install-workflows, /v1/action-workflows, /v1/components/builds/:build_id) have no owning-resource id in the path. Default is fail-closed (safe). Where the read-only UI needs them (workflows, most likely), add an explicit authz check in the handler that reads OwnerID/OwnerType, builds the chain, and calls Authorize. Note OwnerType is an untyped string ("installs"/"apps") — introduce constants as part of this work.
deferred F4 — Deprecated top-level component routes. Only relevant when component is promoted. /v1/components/:component_id carries the component id (direct grants resolve from the path); ancestor grants need the findComponent app lookup. The deepest-param builder handles this uniformly if it Preloads the app.
Confirmed sound: read-only-as-verb (S2), ancestor cascade (S5), name-or-id resolution ordering (S8), cross-org isolation (S9), and independent grant accumulation with any-link/all precedence (S12). The core single-resource path is correct; the gaps are all about collections and routes that don't name their resource.

11. Revised implementation order (post-pressure-test)

  1. ResourceGrant model + migration + AfterQuery aggregation.
  2. Authorize primitive + chain builders for org/app/install (design the builder to select by deepest path param so leaf targets are an additive promotion later).
  3. Org-gate rework with OrgAuthorized (heavy tests vs. existing role types).
  4. Resource authorization folded into the org gate (§8b), enabled by the ResourceGrantsEnabled flag.
  5. Collection-endpoint grant-scope filtering (F1, §8d) — shared scope helper + GORM scopes + OrgAuthorized guard on each list handler.
  6. Grant CRUD endpoints (org-admin only per §9) — single unified surface, see §9a.
  7. Scoped-invite path (§9 grantee scope): extend create_invite.go validation to accept a resource-scoped invite, and make acceptance create the ResourceGrant instead of an org-wide role.
  8. Per-handler checks for out-of-group routes where the read-only UX needs them (F3): start with /v1/workflows/:workflow_id.
  9. UI + CLI for managing grants and scoped invites.
