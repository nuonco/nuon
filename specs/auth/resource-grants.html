Hierarchical Resource Grants

Object-level RBAC for ctl-api — grants that scope an account down to a single app, install, or delegable org-owned resource, alongside the existing org roles.

Status: Implemented on ja/resource-grants-v2, gated behind ResourceGrantsEnabled (default off) · Fallback implementation (request-time owner walk): ja/resource-grants, frozen · Last revised 2026-08-09.

1. Motivation

Before grants, the org roles (org_admin, org_support, installer, runner) all resolved to the same policy: {<orgID>: "all"}. Authorization happened once, in the org middleware, as acct.AllPermissions.CanPerform(org.ID, methodPerm). The role type was effectively metadata — there was no way to say “read-only” or “only this app”.

The original ask was apps_read_only and installs_read_only role types. Investigation showed that scoping to a specific resource fits the existing model almost for free — the permission Set is already map[objectID]Permission. This design adds specific-resource grants, plus per-type wildcards (§9b) for the “all resources of one tier” case.

3. The ownership tree

Every resource has a parent chain terminating at the org. Authorization walks up this chain: a request is allowed if the requested resource or any ancestor carries a grant satisfying the verb. Chains are built from a single org-scoped point read per request — children either carry a direct owner column (components, policy reports) or denormalized install_id/app_id ancestry columns (workflows, runner jobs, queues, log streams, terraform workspaces). There is no request-time recursive owner walk.

org ├─ app chain: app → org <- grant target │ ├─ install chain: install → app → org <- grant target │ │ ├─ install-component (inherits install chain; future target) │ │ ├─ deploys, sandbox runs, stacks, action runs, notebooks, secrets … (inherit) │ │ └─ install runners → their jobs / log streams / queues / workspaces (inherit) │ ├─ component (inherits app chain; future target) │ ├─ builds, branches, branch runs, sandbox builds, action workflows … (inherit) │ └─ workflows, runner jobs, queues, log streams, terraform workspaces │ (polymorphic owners → denormalized install_id/app_id; inherit that tier) ├─ webhook chain: webhook → org <- grant target ├─ vcs_connection chain: vcs_connection → org <- grant target ├─ slack_subscription chain: slack_subscription → org <- grant target └─ org tier (no install/app ancestor): management runner group + its runners/jobs/streams, org queues, triggers, AWS account connections, org settings/team/credentials — org-wide permission only

Grant targets are org, app, install, and the three delegable org-owned siblings webhook / vcs_connection / slack_subscription. Everything else inherits via walk-up; children are never grant targets themselves.

  • Runners are dual-owned. A runner belongs to a runner group, and the group is owned by an install or the org. Install runners inherit their install's chain (an install grantee can see and operate their runner); the management (org) runner group is org tier.
  • The five polymorphic-owner tables (install_workflows, runner_jobs, queues, log_streams, terraform_workspaces) store their grantable ancestry directly: install_id/app_id columns populated at creation (app.ResolveOwnerAncestry) and backfilled by migration 124. Both columns NULL means org tier — a defined state (management-runner jobs, org queues, unresolved legacy rows), never “unknown”; such rows require org-wide permission.
  • Deploys, builds, releases, sandboxes, cloud accounts, audit logs, notebooks are not grant targets — they inherit from their parent install/app via walk-up.

6. Data model

One unified table (internal/app/resource_grant.go), folded into the account's permissions alongside role policies.

ResourceGrant {
  ID, CreatedByID, CreatedAt, UpdatedAt, DeletedAt
  OrgID         // org the grant lives in (drives membership/OrgIDs)
  AccountID
  ResourceType  // org | app | install | webhook | vcs_connection | slack_subscription
  ResourceID    // canonical ID of the granted resource, or "*" (type wildcard)
  Permission    // "read" | "all"
}
// unique on (org_id, account_id, resource_type, resource_id, deleted_at);
// create is an upsert on that key (re-granting updates the permission)

In account.go AfterQuery, after merging role policies:

  • each specific grant merges as {ResourceID: Permission} into AllPermissions;
  • each wildcard grant lands in TypeGrants map[orgID]map[resourceType]Permission (exposed per-org via OrgTypeGrants(orgID)) — kept out of the flat Set so a tier wildcard cannot leak to other tiers;
  • the grant's OrgID joins OrgIDs, so an otherwise org-less account passes org membership.

7. Authorization primitive: walk-up-the-chain

// internal/pkg/authz/authorize.go
type Link struct{ Type, ID string }   // one tier: grant resource type + object id

// most-specific -> least-specific; allow if any link satisfies perm,
// via a specific-object grant (perms) or a tier wildcard (wildcards).
// A Link with empty ID is type-only (creates/collections) and is
// satisfiable only by that tier's wildcard.
func Authorize(perms permissions.Set, wildcards map[string]permissions.Permission,
    chain []Link, perm permissions.Permission) error

Chains per resource, each built from at most one org-scoped point read:

  • org: [org] — the org-admin case is just the last link, unifying the old org gate with grants
  • app: [app, org]; install: [install, app, org] (install row carries app_id)
  • org-owned siblings: [webhook|vcs_connection|slack_subscription, org], or type-only [{type}, org] for their collection/create routes
  • owned children: the owner's chain, read from the child's direct owner column or its denormalized install_id/app_id; both NULL ⇒ bare [org]
  • runners: one fixed hop through the runner group (install- or org-owned; never recursive)

8. Enforcement wiring

8a. Org-gate rework only non-additive change

Resource authorization is folded into the existing org middleware. The whole feature is gated behind one flag, ResourceGrantsEnabled (internal.Config → env RESOURCE_GRANTS_ENABLED, default off). When it is off, the gate behaves exactly as before. When on, org.go splits membership from authorization:

orgErr := acct.AllPermissions.CanPerform(object, perm)
if orgErr == nil {
    cctx.SetOrgAuthorized(ctx, true)                  // org-wide grant/role: fast path
} else {
    if !acct.HasOrg(org.ID) { 403 }                   // not a member at all
    cctx.SetOrgAuthorized(ctx, false)                 // member via a narrow grant; defer
    if !isFilteredCollection(ctx) {
        authorizeResource(ctx, acct, org.ID, perm)    // resolve resource in path + walk up
    }
}

Fail-closed: a deferred request whose route cannot be resolved to a chain (and is not a filtered collection) is denied. Folding enforcement into the org gate (rather than per-group middlewares) means one flag enables the whole feature and there is no flag-on-but-middleware-not-wired gap.

One special case predates grants and is preserved: POST …/components/:component_id/builds checks the org's <orgID>:component_builds object on the fast path (permissions.RequestObject), which the runner role carries.

8b. Route → chain resolution

resourceChain (middlewares/org/org.go, resources.go, owners.go) resolves the most specific resource named by the route, in order:

  1. :install_id param (id-or-name, org-scoped) → [install, app, org]
  2. :app_id param (id-or-name) → [app, org]
  3. org-owned resource prefixes (orgResourceRoutes: webhooks, VCS connections, the Slack surface) → [{type} (+id), org]; routes under the prefix without the id param resolve type-only
  4. owned-child prefixes (ownedResourceRoutes: workflows, runner jobs, queues, log streams, terraform workspaces, runners, top-level components/builds/action-workflows, sandbox runs, stacks, policy reports) → single point read of the owner columns → the owner's chain
  5. parentless creates (POST /v1/installs, POST /v1/apps) → type-only link for the created tier
  6. anything else: fail closed (unless explicitly classified, 8c)

8c. Route-coverage validation boot-time guarantee

Every /v1 route on the public server must be consciously classified: resolvable by 8b, exempt (global/public), a filtered collection (8d), explicitly org-level (orgLevelRoutes: org settings, team/credential surfaces, the grant surface itself, and all org-wide collections/aggregates), or explicitly uncovered (uncoveredRoutes: terraform-backend routes whose owner arrives in the request body, and the trigger family pending a grantable type). ValidateRouteCoverage runs at startup — an unclassified route fails the boot (and CI) of the PR that adds it instead of silently 403ing grant-scoped accounts in production. A snapshot test pins the full route inventory. The complete per-endpoint mapping lives in the authorization audit.

8d. Collection-endpoint grant-scope filtering

Walk-up authorizes a single addressed resource; list endpoints return collections. Four core navigation lists let deferred (OrgAuthorized=false) members through and filter results to entitled rows instead of gating the endpoint: GET /v1/installs, GET /v1/apps/:app_id/installs, GET /v1/apps, GET /v1/components.

  • Shared helper scope.ForList(acct, perm) (internal/pkg/authz/scope) turns the caller's grants into per-tier ID sets — OrgIDs/AppIDs/InstallIDs plus AppWildcardOrgs/InstallWildcardOrgs for type wildcards.
  • Per-table GORM scopes (IDSets.Installs/Apps/Components, column names parameterized for the view-backed tables) drop into .Scopes(...). A row is visible if any tier it belongs to is granted; the Apps scope adds upward visibility — the parent app of a granted install is listed (metadata only; sibling installs stay filtered) so navigation stays coherent.
  • Per-service guards (grant_scope.go in the installs/apps/components services): no-op when cctx.OrgAuthorized (org-wide callers keep their unfiltered plan), the real filter for deferred members, and WHERE 1=0 if no account is resolvable (fail closed).
All other org-wide collections are org-level by design (user decision): GET /v1/builds, /v1/workflows, /v1/runner-jobs, /v1/queues, /v1/terraform-workspaces, /v1/policy-reports, health/label aggregates, etc. enumerate resources across the whole org and require an org-level permission rather than per-grant result filtering. The denormalized ancestry columns make extending filtering to them a mechanical follow-up (each is one WHERE install_id IN (…) away) if a product need appears; detail routes for those resources already resolve per-row, so the lists are navigation, not capability.

8e. Query performance

Every list query AND's an unconditional WHERE org_id = ? before the grant scope, so the OR-of-INs only ever evaluates within one org's rows — never a whole-table scan. For a narrow grantee OrgIDs is empty (an org grant would have taken the fast path), so the effective filter is id IN (…) OR app_id IN (…) [OR org_id IN (wildcard orgs)] over an already-narrow set. Org-wide callers skip the filter entirely — no regression on the large-org path. Two things need active attention as filtering extends: each filtered column stays independently indexed, and pagination COUNT queries apply the same scope (a correctness bug if missed, not just a slow query). If per-account grant cardinality ever reaches thousands, the materialized IN lists can be swapped for a JOIN against resource_grants; not needed at expected scale.

8f. Denormalized ancestry (how children resolve)

The five polymorphic-owner tables carry install_id/app_id directly (see the decision record for the full option analysis vs. nested routes and the request-time walk):

  • Write path: BeforeCreate hooks call app.ResolveOwnerAncestry(tx, orgID, ownerType, ownerID), which maps every owner type observed at the tables' creation sites to its grantable ancestors. Unknown owner types and dangling references resolve to the org tier (never an error — creation must not break). Owners that are themselves denormalized are read from their own columns, so resolution is at most two point queries and never recursive.
  • Backfill: migration 124, batched and idempotent, one targeted update per (table, owner-type) pair; install_workflows first so rows owned by workflow steps read the workflow's fresh columns. Rows whose owners are org-tier (management-runner jobs, org queues, admin-created jobs with no owner, runner-supplied unknown workspace owners) legitimately stay NULL. Rows written by not-yet-updated pods during the deploy rollout stay NULL too — an accepted, fail-closed window.
  • Read path (authorization): denormOwned(table) in middlewares/org/owners.go — one org-scoped SELECT install_id, app_id, then ownerChain. Ownership is create-time-only on all five tables (verified: no code updates owner columns post-insert), so the columns cannot go stale.

How do bare child routes resolve their owner? Denormalized ancestry columns Chosen over (a) a request-time recursive owner walk — built on the frozen ja/resource-grants branch, kept as fallback — and (b) adding owner-nested routes and downgrading bare routes to org-level, which remains available later as an API-surface evolution the columns already enable (nested handlers would scope children with WHERE install_id = ?).

9a. Grant management API implemented: unified surface

Grants are managed through a single resource-agnostic surface — the resource is named in the request body (create) or query (list), not the path. This keeps the API flat as more tiers become grantable and makes the org tier a first-class target with no extra endpoints.

MethodRouteNotes
POST/v1/grantsCreate/upsert (re-granting the same resource updates the permission). Body: { resource_type, resource_id, account_id|email, permission }. resource_type is oneof=org app install webhook vcs_connection slack_subscription; permission is oneof=read all. Apps/installs accept name-or-id (resolved & validated against the caller org); every non-org type accepts the "*" wildcard; org must be the caller's own org. Org-admin only.
GET/v1/grantsList grants in the org; optional ?resource_type=&resource_id= filter.
DELETE/v1/grants/:grant_idRevoke (soft delete). Org-admin only.

Org-wide read is a single org · read grant — it cascades to every descendant via walk-up and is bucketed at the org tier by the collection filter. An app · read grant similarly covers all installs under that app. For “all resources of one tier”, use a type wildcard.

9b. Type-wildcard grants implemented

A grant whose resource_id is "*" scopes to every resource of its resource_type within the org — e.g. { resource_type: "install", resource_id: "*", permission: "all" } grants write on all installs in the org, and crucially not apps or other tiers (which org · all cannot express). Supported for every type except org (already a single resource).

The wildcard deliberately does not reuse the permissions.Set "*" key, which CanPerform falls back to for any object regardless of tier — using it would leak an install · * grant to apps and the org. Instead the tier is carried explicitly:

  • Aggregation (account.go AfterQuery): wildcard grants collect into Account.TypeGrants, keyed by org id then resource type, separate from the flat AllPermissions Set.
  • Walk-up (authz.Authorize): the chain is []Link{Type, ID}; a link is authorized by a specific-object grant or a TypeGrants entry matching that link's tier. An install · * grant matches the install link but never the app or org link. Type-only links (creates, org-resource collections) are satisfiable only by the tier wildcard.
  • Collection filter (scope): IDSets.AppWildcardOrgs/InstallWildcardOrgs widen the list queries to org_id IN (…) for the wildcard tier, with the same upward-visibility semantics as specific grants.

Deferred

  • Execute verb: runbooks/actions want an execute permission, not CRUD. The Permission enum and FromRequest mapping are extensible, so adding it later is additive.
  • Scoped invites: the external-grantee path (§9 resolved table).
  • Leaf-target promotion: component / install-component as grant types; trigger as a delegable org-owned type.
  • Standard roles built on grants: e.g. an Install Manager role whose policy folds in an install · * type grant. Requires the role catalog work (ja/roles, PR #2123) plus a policy-key fold; sequenced after this branch lands.
