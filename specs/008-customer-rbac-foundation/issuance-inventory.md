# Deferred — Credential audience design inventory

**Not part of the RBAC activation release.** All audience implementation, receiver choices and issuer gates below are deferred to a separate project. They do not block the classifier, optional legacy-api readers, standard-role writers or exact conversion in spec 008. `RA` below refers only to that deferred project's hypothetical audience-compatible release.

Source baseline: `eb6e10226` on `ps/rbac-activation-plan`, 4 November 2026. This is retained source research, not a token backfill, writer implementation, or proof of deployed credential use. Keep it uncommitted with spec 008.

## Audience labels are proposals, not existing constants

P, M, R and S below denote proposed configured public API, MCP, runner and stack resource identifiers. Their exact strings and OAuth resource mapping are deferred. Existing `permissions.APICtl`, `APIRunner` and `APIStack` are the existing **role-policy guard**, not a token audience registry. Existing `app.Token` has no audiences field.

Preserve the accepted defaults: fresh login/CLI P+M; approved resources for OAuth; P by default for ordinary customer service tokens with authorized explicit additions; purpose-fixed managed credentials. A token may carry several approved identifiers, never an `all` wildcard. Issuance endpoint, token type, email and role name are not trusted purpose evidence.

All paths below need coverage, including alternate constructors and expiry extensions. Missing `ManagedServiceAccount` does not prove that an account belongs to an ordinary customer: runner, log-stream and federation accounts use other ownership records.

Paths below are relative to `services/ctl-api/`, except where explicitly marked.

## Decisions and evidence still needed before writers

1. Choose concrete configured audience identifiers and trusted OAuth resource mapping; do not infer them from Host headers or reuse role guards as the registry.
2. Settle session/auth-cookie and admin-dashboard receiver semantics without implicitly granting privileged audiences to all login/CLI credentials.
3. Classify version phone-home across public/runner endpoints, and establish the purpose of duplicated stack endpoints.
4. Decide action-environment credential ownership and receiving APIs. This is a real exception to a universal runner-account audience.
5. Define trusted historical ownership resolution for runner, log-stream and federation accounts, including missing/deleted/conflicting records. Absence of a managed binding is not an ordinary-account fallback.
6. Trace external phone-home scripts and seed/integration/canary consumers before enabling those writer families.

These would be activation gates for a future audience project only. No issuer or receiver changes are part of the current activation. The active classifier snapshot contract now lives solely in [spec 008](prompt.md#4-classify-exact-source-records-not-role-labels).
