1. Ship today’s boundaries on the new foundation

Adopt 006’s catalog, policy, scope and evaluator model without requiring its full security cutover. Start with today’s Read-only (org_read_only) and Admin (org_admin) at org scope, then include recognized machine-policy shapes using separate permissions and scopes. Preserve who can access what. Later resource-boundary changes must be explicit increments.

In this activation Out of scope
Minimal Reader {org.read} and Admin {org.read, org.write} bundles; exact scoped compatibility grants Org Editor, new customer role-management APIs, route remaps
Exact existing v1/v2 standard-role conversion, followed by recognized machine shapes once writers are ready Unknown/custom policy inference, historical grant repair, promising zero legacy rows
Optional legacy api metadata to preserve existing restrictions Token audiences, OAuth resource approval, issuer or credential rewrites
Existing API guards, token restrictions, Admin-only checks and transport distinctions Moving enforcement, tighter security boundaries, role-guard retirement
One skip-version-capable release, accepting transient mixed-version errors Mandatory intermediate releases, zero-downtime activation gate, separate apply CLI
Existing migrator, atomic row updates, idempotent conversion Migration-harness rewrite, new scheduler/progress tables, global mutation locks

The model remains identity-neutral: all accounts use roles, policies and the same matcher. There is no customer-only permission category. New recognized machine/private roles use scoped documents. Exact Support/Installer/Runner org-wide grants reuse the full-access bundle without changing role identity. Builder, hosted-installer and unknown custom shapes remain legacy, as does main’s newer log-stream role; conversion requires exact contents and verified ownership, not role-name inference. Preserve log-stream creation and its existing runner API restriction without adding log-stream documents or broadening this converter. No new account, binding, token, OAuth, invitation or workflow schema is needed for the scoped extension.

The previous audience redesign is deferred in its entirety. Its source inventory is future design material, not a dependency or acceptance gate here. Action tokens, session/admin cookies, specialized phone-home receivers and historical credential ownership do not need redesign to convert these two standard roles. No new token audience column, validation, backfill, rotation, consent flow or issuer default is introduced.

The rebased main includes #3197, which blocks REST writes for read-only OAuth tokens. Preserve it. Earlier foundation evidence describing REST/MCP differences predates that change; do not restore the earlier REST behavior or tighten other credential behavior incidentally.

2. Data model and document contract

flowchart LR
    A[Account] --> B[AccountRole]
    B --> C[Role]
    C --> D[Policy]
    B --- E[Trusted OrgID supplies tenant]
    C --- F[RoleType is identity; Version is bookkeeping]
    D --- G[Document NULL: legacy hstore]
    D --- H[Document present: org bundle or scoped rules]

The deployed foundation adds nullable Policy.Document JSONB without a default or index. AccountRole.OrgID remains the binding’s tenant. Org bundles use that org as their scope; resource rules name their narrower scope in the policy. Existing role IDs, contexts, metadata, associations and Admin identity are retained. No binding schema changes or OrgGrant abstraction are needed; use ScopedPermissions{Scope, Permissions}.

Persisted state Reader contract
SQL NULL document Use legacy hstore and existing v1/v2 interpretation.
Present document Use v3 independently of Role.Version; do not retry legacy on error.
JSON null, malformed/unsupported document, or document with nonempty hstore Fail loading; no fallback or partial authority.
Valid document with stale Role.Version Document still selects v3. Do not reject solely for bookkeeping drift.
SQL NULL document with Role.Version 3 Legacy branch; never reconstruct authority from the role label.

Hstore and document must be fetched from the same policy row. Separate role/policy preloads can observe stale bookkeeping without choosing the wrong format. This does not introduce new atomic revocation semantics.

Document []byte stays absent from public JSON and included in Temporal serialization. Its byte representation preserves SQL NULL versus the JSON literal null; the current converter’s json.RawMessage roundtrip does not.

Optional api preserves old behavior; it is not new token audience support

Exact v1 Reader after conversion:

{"kind":"bundle","binding_kind":"org","permissions":["org.read"]}

Exact v2 Admin after conversion, also the shape for newly created Admin roles:

{"kind":"bundle","api":"ctl-api","binding_kind":"org","permissions":["org.read","org.write"]}
Field Contract
kind Required, bundle or resource_rules. Each has its own strictly decoded fields.
binding_kind Required, exactly org. Org identity comes from trusted records, not the document.
permissions Required non-null array for a bundle, or within each resource rule. Empty grants nothing; writers sort/deduplicate. No bare CRUD strings or wildcard permissions.
rules Required non-null array only for resource_rules. Each rule has an explicit scope and permission array; empty grants nothing.
api Optional. Absence contributes no legacy API restriction. Present values must be ctl-api, runner or stack; null, empty, unknown, all and wrong types are rejected.

Reject unknown/duplicate fields, malformed JSON and trailing data. Duplicate fields must be rejected before JSONB normalization. Use the existing permissions.Policy codec, not a third document format or public wrapper type.

The pure codec understands the catalog without classifying principals. Org-bundle runtime integration accepts only empty, minimal Reader and minimal Admin sets. Resource-rule integration accepts the exact mappings below. Other codec-valid sets, such as {org.write} or {org.read, install.read}, must fail integration explicitly, not grant all, disappear silently or fall back to hstore. Permission applicability belongs in the matcher; the compatibility adapter separately limits what can be represented by today’s route verbs and response maps.

The deployed R1 codec requires api. The next reader release accepts its absence and preserves absence when serializing. This is an explicit compatibility extension: R1 cannot read audience-neutral documents.

Scoped rules separate what from where

An install’s telemetry grant is represented as:

{
  "kind": "resource_rules",
  "binding_kind": "org",
  "rules": [
    {"scope": {"kind": "install", "id": "install_acme"}, "permissions": ["telemetry.all"]}
  ]
}

The same install scope can carry stack.all, independently or alongside telemetry.all. Neither implies install.all, org access, or phone-home access. The org comes only from the validated role/policy/binding records; scope.org_id is rejected. Scope IDs must be explicit, without wildcard or legacy-key separators.

Existing scalar grant V3 scope V3 permission Preserved operation boundary
<org>:install/<install> → all install / install ID install.all Exact install object, not every child namespace
<org>:telemetry/<install> → all install / install ID telemetry.all Only that install’s telemetry object
<org>:stack/<install> → all install / install ID stack.all Only that install’s stack object
<org>:runner-job/<job> → all runner-job / job ID runner_job.all Only that job object
<org>:phone_home/<version> → create phone_home / stack-version ID phone_home.create Create on that exact version callback only

phone_home scope names an exact stack-version callback, not an install. Conversion must preserve that version ID. An install-wide phone-home permission would broaden historical access to other versions and is not enabled by this extension. A future explicit install-wide grant would need server-resolved version→install ownership.

The .all IDs are named, finite catalog bundles, not prefix wildcards. The pure matcher recognizes their explicitly listed operations only within the bundle’s target kind; stack.all must not gain phone-home access through the existing stack.report permission. New catalog members do not automatically join a bundle. The legacy adapter preserves the old scalar all behavior, including its existing unknown-verb behavior, on the exact original key.

Multiple permissions at the same install scope can share a rule. Rules that produce the same legacy object twice are rejected rather than applying order-dependent intra-document merging. Across roles, the existing reducer remains unchanged. Its surviving sources keep separate permission sets so one surviving namespace cannot resurrect another.

No resource existence scan is added to request authentication. Existing route ownership checks remain responsible for resolving resources. The planned converter must independently validate source ownership before writing rules.

3. Keep authorization and wire behavior unchanged

APIFromRole inspects documents before its legacy version check. For document policies, a missing api contributes no restriction even with Version 3; a present value retains its restriction. Legacy v1/v2 behavior remains unchanged, including errors for malformed v2 API metadata. No api: all, role-name inference or implicit ctl-api default.

Keep APIForRoles and assignment compatibility checks at their existing sites. REST continues to consider the entire account role set, including other orgs. MCP does not acquire that whole-account API guard. Existing MCP static-token, account-type and membership checks remain. The shared permission loader must not become a new audience gate.

For document-backed roles, validate one live policy and live bindings/accounts/orgs, matching RoleID and OrgID across associations. Never infer missing ownership from request headers or silently repair bindings. The merged unique live account-role index remains a prerequisite, not new cleanup work in this branch.

The compatibility reducer preserves the supplied Roles sequence: first all survives; otherwise the last scalar contribution wins for an object. Only surviving contributions reach the v3 matcher or legacy adapter. Do not allow an overwritten read grant to reappear through an independent old/new union. Response projection is not authority

Keep Account.permissions and policy permissions as string maps. Minimal Reader projects org → read; Admin projects org → all. Scoped rules project their exact original resource key and scalar verb, never the parent org or another namespace. Include the api entry only when it is actually retained in the document. Empty policies without api project an empty map. Do not manufacture an api entry or persist the projection.

Existing decisions continue using loaded authority, not response maps. Keep public/internal serialization and Temporal raw-policy roundtrips compatible. No public API schema or client shape changes are required.

4. Classify exact source records, not role labels

The classifier now covers the five standard org-role types and the five recognized scoped role types. Scoped runtime support alone is insufficient: conversion independently verifies the source grant and its ownership records.

authz.ClassifyOrgRole is pure and shared by inventory and the converter. It returns eligible with the typed target policy, permission IDs and optional legacy API metadata, already_v3, a named skipped reason, or an invalid-document error. It does not write records, encode an alternative format, repair bookkeeping or infer a document from a role name.

Source Disposition
Live v1 standard Reader/Admin with exact {org: read/all} Eligible without api.
Live v2 standard Reader/Admin with exact {org: read/all, api: ctl-api} Eligible retaining ctl-api.
Exact Support/Installer/Runner {org: all} Eligible without api at v1; v2 retains ctl-api for Support/Installer or runner for Runner. RoleType is unchanged.
Exact runner-install, runner-job, stack, telemetry or version-phone-home shape Eligible after scoped ownership checks; v1 omits api, v2 retains the valid stored API.

Builder/hosted-installer/unknown custom roles; other versions or shapes Leave legacy and report reason.
Missing/deleted/mismatched ownership, duplicate bindings or standard roles, ambiguous custom combinations Skip/review; no repair or grant resurrection.
Present malformed/nonminimal document or conflicting hstore Error, never fallback or successful conversion.

Require exactly one live policy with matching role/org ownership. An unbound standard org role is valid. V1 with extra api metadata, extra resource/wildcard keys or custom CRUD values is not an exact candidate. New role metadata is not proof of old policy contents. Standard org roles with private ownership remain excluded. Scoped roles require exactly one live service-account binding, no managed-role flag or selectable contexts, and matching live resource/org relationships.

Runner-install ownership follows the account’s exact subject to a runner, or a job then its runner, and checks the runner group’s install owner. Stack ownership follows the subject to its install stack. Runner-job ownership checks the subject against the exact job. These paths accept historical missing managed-account rows only with that live resource evidence. Telemetry and phone-home require explicit managed ownership. Phone-home additionally verifies the exact version, stack and install chain, and the binding’s version instance key. Present deleted/conflicting managed ownership is never treated as missing. Private-role references must agree with the bound account. Missing/deleted or ambiguous sources are skipped, not repaired; no subject/email heuristics or install-wide callback inference.

Load raw snapshots without runtime Account/Policy projection hooks. OrgRoleSnapshot.Role includes its actual org and all live raw policies; OrgRoles includes live same-type roles for standard-role uniqueness. Bindings includes all live bindings to the source and their actual accounts. Standard candidates also load holder roles/raw policies; scoped candidates instead load Resource ownership records by exact IDs. Private comes from managed ownership references. Scoped candidates do not scan every role in their org. Missing/deleted records remain observable.

Keep bounded source loading and stable-ID enumeration outside the classifier. A disposable read-only harness is sufficient; no startup scan, public endpoint, permanent apply command or feature flag. Report raw population counts and exceptions independently of eligibility, including policies with no live owner. Resource IDs belong in restricted logs, not metric labels. Refresh production classification before activation.

Accepted single-release rollout

Ship compatible readers and reconcilers, all recognized v3 creation paths, and the expanded converter together. Customers may upgrade directly from supported legacy versions. Do not require the separately prepared ps/rbac-compatibility artifact to be deployed first; preserve it as a recovery candidate, not a rollout dependency.

Accepted effects during upgrade:

  • Old APIs/workers can reject converted policies until replaced. Temporary request and workflow-activity failures are accepted, not evidence of changed intended permission semantics.
  • Legacy roles created after the converter passes can remain legacy. New readers support them; a future explicitly numbered catch-up migration can handle them. Zero legacy rows is not an acceptance criterion.
  • No maintenance window, global mutation pause, audience redesign or runtime activation flag is required by this plan.

Failures must settle after all target processes are running. Persistent mixed authority, permission broadening, silent historical-migration corruption and rollback to incompatible readers remain outside that acceptance.

Deployment ordering established from source

  • Cloud: mono/services/ctl-api/k8s/templates/startup.tpl runs the target image’s startup as a Helm pre-install,pre-upgrade hook. Old APIs/workers remain live during migration. nuonctl enables RollbackOnFailure; Helm rollback does not undo database conversion.
  • BYOC AWS/GCP: deploy_control_plane deploys the chart, then invokes the post-deploy startup action. The pinned charts start API containers normally while the startup deployment waits for an explicit exec. Both startup actions default SCALE_DOWN=false; optional draining continues after timeout and is not a strict compatibility barrier.
  • These are repository-source observations, not a census of every customer’s installed configuration.

Conversion mechanics

The retained converter (originally 153-convert-standard-org-roles, pending renumbering) uses the existing startup framework and 100-role stable-ID batches, not offsets over a shrinking cohort. Re-read and classify each candidate and its associations in a short repeatable-read transaction, locking the candidate role and its live policies. Use raw scans to avoid runtime projection hooks. Conditionally update the policy row’s document and clear hstore together, verifying the original full shape. Update Role.Version to 3 in that same transaction; require expected affected-row counts and roll back on failure. Preserve policy/role/binding IDs and metadata. Changed candidates are reclassified or skipped, not overwritten. Concurrent source updates that invalidate the snapshot propagate a serialization failure; reinvocation reclassifies the current state. There is no unbounded retry loop or global lock on role assignment.

Already-converted rows are no-ops. Partial conversion leaves readable mixed-format data; reinvocation processes the remaining eligible rows. Malformed/unsupported present documents propagate errors. Measure a representative run against the existing startup timeout before deciding whether its existing override is needed.

Normal valid assignment/removal may overlap conversion: bindings reference existing roles rather than copying policy data. Do not add shared role locks to every writer or pause all membership/machine provisioning. If a writer can mutate a candidate policy incompatibly, handle that specific conflict before rollout.

Accepted harness assumption: scheduling, claims, status persistence and retry delivery belong to the existing migrator. Its known recovery/reporting issues remain separate maintenance work. PR 7 owns atomicity, idempotency, accurate results and error propagation when called, not a framework rewrite or process-crash recovery subsystem.

Rollback floor and completion

The first document without api raises the rollback floor to the compatible reader release; R1 would reject it. Do not remove a retained api restriction to bypass validation, restore hstore speculatively, or roll back to an incompatible reader. Keep legacy API guards indefinitely until their own separately reviewed cutover.

The first resource_rules document additionally requires scoped readers for successful requests. The optional-api-only checkpoint cannot read it. Old-process failures during replacement are accepted; those processes cannot be a recovery target after activation.

A recovery image must include document-aware reconciliation and stack adoption. The bare scoped-reader checkpoint 0f60e62359 is not safe: it lacks document-aware reconciliation and stack adoption. Any recovery deployment must preserve the schema, binding index and stored documents; do not roll back to the merged foundation or restore hstore. The former A/B/C labels describe historical packaging only, not mandatory sequential deployments.

If a compatible recovery image resumes v2 creation after conversion was recorded, reclassify and add an explicit catch-up migration when needed. Startup does not rerun an applied migration. Do not add hypothetical catch-up code now. Completion means new standard creation is v3 and exact conversions/exceptions are accounted for—not zero legacy rows.

Ownership/identity drift Deleted/missing/mismatched associations, duplicate bindings/roles, private roles; Support/all does not become Admin
Wire/serialization regression Account/policy maps, empty bundles, raw policy Temporal roundtrip, no persisted projection
Writer or converter scope creep Existing standard policy bytes unchanged under reconciliation; exact recognized new-role shapes switch; unsupported records stay legacy
Scoped grant broadening Same install ID across telemetry/stack/install; sibling install/job/version and foreign org denials; phone-home create versus read/update/delete; no install-wide callback inference
Named bundle overreach Explicit bundle membership, target-kind restriction, missing/wrong ceiling, no stack.report access to phone-home through stack.all
Migration correctness Transaction rollback between updates, partial run/reinvocation, source edit, concurrent valid assignment/removal, all-ineligible no-op

Use existing logs/metrics for scanned/eligible/skipped/converted/failed counts and affected denial/load-error rates. No new dashboard, events, high-cardinality metrics or full-platform journey certification is required.

Token-owned audiences remain a possible later design direction. The deferred inventory records issuer/receiver findings without making its open choices blockers here.
