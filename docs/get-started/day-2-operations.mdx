## Workflows

A workflow is the lifecycle of an install or a component. It plans the change, surfaces a diff, runs through any approvals you've configured.

Each workflow run's logs and step state are visible in the dashboard, CLI, and TUI.

[How it works → Workflows](/concepts/workflows)

## Health Checks

Nuon checks component health on every install, with no agent to install. Helm chart and Kubernetes manifest
components are checked about once a minute. Terraform components get a health status when you add an HTTP or TCP
probe, or a custom check.

When a component or an install becomes unhealthy, and when it recovers, Nuon alerts the Slack channels and webhooks
you subscribe. Each component and install keeps 90 days of timeline and uptime.

[How to → Health Checks](/guides/health-checks)

## Install Telemetry

Install telemetry is the logs, metrics, and traces your application produces while running in a customer's cloud
account. Nuon can forward this data to your observability backend so you can monitor performance and troubleshoot
issues across installs.

Forwarding is off by default. It needs a Nuon BYOC deployment, and Nuon enables the relay with you. Without it, Nuon
stores only the logs of its own operations and the output of your actions. Application logs stay in the customer's
account.

[How it works → Install Telemetry](/concepts/install-telemetry)

## Audit Logs

Install runners on AWS, Azure, and GCP can forward deployment, action workflow, and sandbox audit events directly to a
customer-controlled OTLP logging backend. The destination and credentials remain in the customer's cloud account. Only
Nuon audit events are forwarded, not application logs or general runner logs.

[How to → Export Runner Audit Logs](/guides/export-runner-audit-logs)

## Actions

An action is a script you run on a live install. The runner executes it inside the customer's account, so you need no
SSH or `kubectl` access to the customer's network. Define it in TOML, point it at a repo, and set environment
variables. It runs on a cron schedule, on a lifecycle event such as `post-deploy-component` or `pre-reprovision`, or on
a manual trigger. The output and run history stay in Nuon.

During an incident, run a one-off command with an [adhoc action](/guides/adhoc-actions) without changing your app
config. Chain actions and deploys into a repeatable procedure with a [runbook](/concepts/runbooks).

Typical uses: [database migrations](/guides/database-migrations), maintenance scripts, collecting logs, and custom
checks that the built-in [health checks](/guides/health-checks) do not cover.

[How it works → Actions](/concepts/actions)

## Database Migrations

There are three ways to run migrations across installs: a Kubernetes Job that an action starts after each deploy, an
init container in your app's pods, or an action that runs a container image on the install runner. Use an action with a
`pre-deploy-component` trigger when the migration must finish before new pods start. A failed migration action pauses
the deploy until someone retries or skips it. To stop the deploy when a migration keeps failing, run both as steps of
a [runbook](/concepts/runbooks).

[How to → Database Migrations](/guides/database-migrations)

## Policies

A policy is an OPA or Kyverno rule that gates what can be deployed. Policies validate Terraform plans, Helm charts, Kubernetes manifests, container images, and sandbox configurations before they apply. Every evaluation is logged on a per-app analytics page, scoped to the install, component, action, or deploy that triggered it.

Use policies to enforce compliance, security baselines, or organization conventions across every customer install at once, instead of relying on review discipline per install.

[How it works → Policies](/concepts/policies)

## Operation Roles

An operation role is a specific IAM role the runner assumes for one class of work: provisioning, deploys, or individual actions. For urgent elevated access, use [break glass](/concepts/break-glass) roles. Each role is defined by the vendor and approved by the customer through the Stack, so the runner never holds more permissions than the task at hand requires.

Roles can be scoped per component or per action; every workflow run records which role was used.

[How it works → Operation Roles](/concepts/operation-roles)
