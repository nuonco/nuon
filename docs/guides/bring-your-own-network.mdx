Many customers have existing AWS VPCs or Kubernetes clusters they want to use for BYOC deployments. Nuon supports three deployment models to meet different infrastructure requirements:

| Model | Network | Cluster | Best For |
|-------|---------|---------|----------|
| **Standard** | Nuon creates VPC | Nuon creates EKS | Full isolation, new deployments |
| **BYO-VPC** | Customer provides VPC | Nuon creates EKS | Network compliance, co-location |
| **BYO-EKS** | Customer provides VPC | Customer provides EKS | Existing infrastructure, consolidation |

## When to Use Each Model

**Standard (Nuon Managed)**: Best when customers want complete isolation and don't have existing infrastructure requirements. Nuon provisions everything.

**BYO-VPC**: Best when customers have:
- Compliance requirements for specific network configurations
- Existing VPCs with peering, transit gateways, or VPN connections
- Applications that need to communicate with resources in an existing VPC

**BYO-EKS**: Best when customers have:
- Existing Kubernetes clusters with established policies and monitoring
- Desire to consolidate workloads on shared infrastructure
- Specific cluster configurations (node types, autoscaling, add-ons)

## BYO-VPC: Install into an Existing VPC

With BYO-VPC, customers provide their existing VPC and subnet information. Nuon creates a new EKS cluster within that VPC.

### Requirements

The customer's VPC must have:

- **Private subnets** with outbound internet access (via NAT Gateway) for pulling container images
- **Public subnets** for load balancers (if using public-facing services)
- **A subnet for the Nuon runner** with outbound internet access

<Note>
The Nuon runner operates on a standalone EC2 Auto Scaling Group, not inside the EKS cluster. This ensures consistent, isolated deployment capabilities.
</Note>

### Configuration

#### inputs.toml

Define inputs to collect the customer's VPC and subnet information:

```toml inputs.toml
#:schema https://api.nuon.co/v1/general/config-schema?type=inputs

[[group]]
name = "network"
display_name = "Network Configuration"
description = "Provide your existing VPC details"

[[input]]
name = "vpc_id"
display_name = "VPC ID"
description = "ID of your existing VPC (e.g., vpc-abc123)"
required = true
sensitive = false
group = "network"

[[input]]
name = "private_subnet_ids"
display_name = "Private Subnet IDs"
description = "Comma-separated list of private subnet IDs for the EKS cluster"
required = true
sensitive = false
group = "network"

[[input]]
name = "public_subnet_ids"
display_name = "Public Subnet IDs"
description = "Comma-separated list of public subnet IDs for load balancers"
required = true
sensitive = false
group = "network"

[[input]]
name = "runner_subnet_id"
display_name = "Runner Subnet ID"
description = "Subnet ID for the Nuon runner (must have outbound internet access)"
required = true
sensitive = false
group = "network"
```

#### sandbox.toml

Use the standard EKS sandbox - it receives VPC information from the install stack:

```toml sandbox.toml
#:schema https://api.nuon.co/v1/general/config-schema?type=sandbox

terraform_version = "1.11.3"

[public_repo]
repo = "nuonco/aws-eks-sandbox"
directory = "."
branch = "main"

[vars]
cluster_name = "n-{{.nuon.install.id}}"
# VPC parameters flow from the CloudFormation stack
vpc_id = "{{.nuon.install.inputs.vpc_id}}"
private_subnet_ids = "{{.nuon.install.inputs.private_subnet_ids}}"
public_subnet_ids = "{{.nuon.install.inputs.public_subnet_ids}}"
```

## BYO-EKS: Install into an Existing Kubernetes Cluster

With BYO-EKS, customers provide both their VPC and an existing EKS cluster. Nuon deploys components directly into the existing cluster without creating new infrastructure.

### Requirements

The customer's EKS cluster must have:

- Kubernetes version 1.27 or later
- OIDC provider configured for IAM Roles for Service Accounts (IRSA)
- Adequate node capacity or cluster autoscaling configured
- Network connectivity between the runner subnet and the cluster

### Configuration

#### inputs.toml

Collect both cluster and network information:

```toml inputs.toml
#:schema https://api.nuon.co/v1/general/config-schema?type=inputs

[[group]]
name = "cluster"
display_name = "Cluster Configuration"
description = "Provide your existing EKS cluster details"

[[input]]
name = "cluster_name"
display_name = "EKS Cluster Name"
description = "Name of your existing EKS cluster"
required = true
sensitive = false
group = "cluster"

[[group]]
name = "network"
display_name = "Network Configuration"
description = "VPC configuration for the runner"

[[input]]
name = "vpc_id"
display_name = "VPC ID"
description = "VPC ID where your cluster runs"
required = true
sensitive = false
group = "network"

[[input]]
name = "private_subnet_ids"
display_name = "Private Subnet IDs"
description = "Comma-separated list of private subnet IDs"
required = true
sensitive = false
group = "network"

[[input]]
name = "public_subnet_ids"
display_name = "Public Subnet IDs"
description = "Comma-separated list of public subnet IDs"
required = true
sensitive = false
group = "network"

[[input]]
name = "runner_subnet_id"
display_name = "Runner Subnet ID"
description = "Subnet for the Nuon runner (must have outbound internet access)"
required = true
sensitive = false
group = "network"
```

#### sandbox.toml

Use the BYO-EKS sandbox, which reads the existing cluster instead of creating one:

```toml sandbox.toml
#:schema https://api.nuon.co/v1/general/config-schema?type=sandbox

terraform_version = "1.11.3"

[public_repo]
repo = "nuonco/aws-byo-eks-sandbox"
directory = "."
branch = "main"

[vars]
# Reference existing cluster
cluster_name = "{{.nuon.install.inputs.cluster_name}}"
# VPC parameters
vpc_id = "{{.nuon.install.inputs.vpc_id}}"
private_subnet_ids = "{{.nuon.install.inputs.private_subnet_ids}}"
public_subnet_ids = "{{.nuon.install.inputs.public_subnet_ids}}"
```

<Note>
The `aws-byo-eks-sandbox` uses Terraform data sources to read the existing cluster configuration. The sandbox outputs remain compatible with standard components, so your Helm charts and Kubernetes manifests work without modification.
</Note>

## Subnet Tagging (Alternative Method)

For BYO-VPC scenarios, you can alternatively use subnet tags instead of explicit subnet ID inputs. This is useful when customers prefer not to enter specific subnet IDs.

### Required Tags

Tag subnets in the target VPC:

| Subnet Type | Tag Key | Tag Value |
|-------------|---------|-----------|
| Private subnets | `kubernetes.io/role/internal-elb` | `1` |
| Public subnets | `kubernetes.io/role/elb` | `1` |

### Using Tags with ECS

The AWS ECS BYOVPC sandbox supports automatic subnet discovery:

- Tag public subnets with `visibility:public`
- Tag private subnets with `visibility:private`
- Or provide explicit subnet IDs via inputs (which override tagged subnets).

## Troubleshooting

### Runner cannot reach the cluster

Ensure the runner subnet has:

- A route to the cluster's VPC CIDR
- Security group rules allowing outbound HTTPS (443) to the cluster endpoint

### Components fail to deploy

For BYO-EKS, verify:

- The cluster's OIDC provider is configured
- Node groups have capacity for new pods
- The Nuon runner has cluster access (EKS access entries are created automatically)

### Subnets not found

If using subnet tagging:

- Verify tags are applied correctly (`kubernetes.io/role/internal-elb:1`)
- Check that subnets are in the same VPC as specified

If using explicit subnet IDs:

- Verify the subnet IDs are correct and exist
- Ensure subnets belong to the specified VPC

## Azure BYO-VPN

For Azure deployments, use the Azure AKS BYOVPN sandbox:

```toml inputs.toml
#:schema https://api.nuon.co/v1/general/config-schema?type=inputs

[[input]]
name = "resource_group_name"
display_name = "Resource Group Name"
description = "The Resource Group containing your VPN"
required = true
sensitive = false

[[input]]
name = "network_name"
display_name = "Network Name"
description = "The VPN to install the app in"
required = true
sensitive = false

[[input]]
name = "subnet_name"
display_name = "Subnet Name"
description = "The Subnet within the VPN"
required = true
sensitive = false
```

```toml sandbox.toml
#:schema https://api.nuon.co/v1/general/config-schema?type=sandbox

terraform_version = "1.11.3"

[public_repo]
repo = "nuonco/sandboxes"
directory = "azure-aks-byovpn"
branch = "main"

[vars]
resource_group_name = "{{.nuon.install.inputs.resource_group_name}}"
network_name = "{{.nuon.install.inputs.network_name}}"
subnet_name = "{{.nuon.install.inputs.subnet_name}}"
```

```toml runner.toml
#:schema https://api.nuon.co/v1/general/config-schema?type=runner

runner_type = "azure-aks"
```
