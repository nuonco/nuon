This guide shows how to define operation roles, assign them to operations, and override them for a single run. For
what operation roles are and how Nuon picks one, see [Operation Roles](/concepts/operation-roles).

## Example: separate deploy and teardown roles

This example gives an `api` component one role to deploy and another to tear down, so a deploy can't delete anything.

<Steps>
  <Step title="Define the roles">
    Add two custom roles to `permissions.toml`:

    ```toml permissions.toml
    [[roles]]
    type        = "custom"
    name        = "{{.nuon.install.id}}-api-deploy"
    description = "Create and update the API's Lambda function"

    [[roles.policies]]
    name     = "api-deploy"
    contents = """
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Action": ["lambda:CreateFunction", "lambda:UpdateFunctionCode", "lambda:GetFunction"],
          "Resource": "*"
        }
      ]
    }
    """

    [[roles]]
    type        = "custom"
    name        = "{{.nuon.install.id}}-api-teardown"
    description = "Delete the API's Lambda function"

    [[roles.policies]]
    name     = "api-teardown"
    contents = """
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Action": ["lambda:DeleteFunction", "lambda:GetFunction"],
          "Resource": "*"
        }
      ]
    }
    """
    ```
  </Step>
  <Step title="Assign them to the component">
    ```toml components/api.toml
    [[operation_roles]]
    operation = "deploy"
    role      = "{{.nuon.install.id}}-api-deploy"

    [[operation_roles]]
    operation = "teardown"
    role      = "{{.nuon.install.id}}-api-teardown"
    ```
  </Step>
  <Step title="Ship it">
    Push to your app branch, then [reprovision](/guides/reprovision-installs) existing installs so their stacks create
    the new roles.
  </Step>
  <Step title="Check it">
    The component's next deploy shows the `api-deploy` role in the dashboard.
  </Step>
</Steps>

## Define your own roles

Your app config must define a provision, maintenance, and deprovision role. Declare them, and any roles of your own, in
one of two layouts:

- **`permissions.toml`:** one `[[roles]]` block per role, each with a `type`.
- **`permissions/` directory:** one file per role, such as `permissions/maintenance.toml`, each with a `type`.

Use one layout, and declare each standard role once. If two roles share a standard type, Nuon uses the last one
without an error.

Add your own roles with `type = "custom"`:

```toml permissions.toml
[[roles]]
type        = "custom"
name        = "{{.nuon.install.id}}-deploy-role"
description = "Role for Lambda deployments"

[[roles.policies]]
name     = "lambda-deploy"
contents = """
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["lambda:CreateFunction", "lambda:UpdateFunctionCode"],
      "Resource": "*"
    }
  ]
}
"""
```

Existing installs get a new role the next time their stack is updated. See
[Reprovision installs](/guides/reprovision-installs).

## Template role names

Role names support the same Go template syntax used elsewhere in Nuon config:

```toml
role = "{{.nuon.install.id}}-deploy-role"
```

Common template variables:

| Variable                                       | Description                                        |
| ---------------------------------------------- | -------------------------------------------------- |
| `{{.nuon.install.id}}`                         | Install ID, ensures each install gets its own role |
| `{{.nuon.install.sandbox.outputs.<key>.name}}` | Sandbox stack output values                        |

The rendered name must match a role in your permissions or break glass config. If it doesn't, the run uses
the default role.

## Named IAM policies

Named IAM policies are standalone, customer-managed policies that AWS CloudFormation stacks create before any role.
Define each one in `permissions/policies/`, then attach it by name to any operation role or
[break glass role](/concepts/break-glass). This uses the `permissions/` directory layout. With `permissions.toml`,
declare them as `[[named_policies]]` blocks in that file instead. Use them to share one policy across several roles, or to split a large permission set that would exceed
AWS's inline policy size limit.

```toml permissions/policies/rds-admin.toml
name        = "{{.nuon.install.id}}-rds-admin"
description = "Manage this install's RDS cluster"
contents    = """
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["rds:ModifyDBCluster", "rds:RebootDBInstance"],
      "Resource": "*"
    }
  ]
}
"""
```

```toml permissions/maintenance.toml
type        = "maintenance"
name        = "{{.nuon.install.id}}-maintenance"
description = "Day-2 operations"

[[named_policies]]
name = "{{.nuon.install.id}}-rds-admin"
```

The `name` in `[[named_policies]]` must match a policy defined under `permissions/policies/`. Named policies are created
even when the role that attaches them is disabled. The install stack outputs a `named_policy_arns` map of policy name to
ARN, so components can attach a policy to other roles, such as a Kubernetes workload's IAM role.

## Assign a role to one entity

Set a role directly on a sandbox, component, or action config. It takes precedence over matrix rules.

### Sandbox (`sandbox.toml`)

Use an `[[operation_roles]]` array to map sandbox operations to roles.

```toml sandbox.toml
[[operation_roles]]
operation = "provision"
role      = "{{.nuon.install.id}}-sandbox-deploy-role"

[[operation_roles]]
operation = "reprovision"
role      = "{{.nuon.install.id}}-sandbox-update-role"

[[operation_roles]]
operation = "deprovision"
role      = "{{.nuon.install.id}}-sandbox-teardown-role"
```

Valid operations for sandbox: `provision`, `reprovision`, and `deprovision`.

### Components (`components/<name>.toml`)

Use the same `[[operation_roles]]` array on any component config file.

```toml components/my_lambda.toml
[[operation_roles]]
operation = "deploy"
role      = "{{.nuon.install.id}}-deploy-role"

[[operation_roles]]
operation = "teardown"
role      = "{{.nuon.install.id}}-teardown-role"
```

Valid operations for components: `deploy` and `teardown`.

### Actions (`actions/<name>.toml`)

Actions use a single top-level `role` field. To run an action with a
[break glass role](/concepts/break-glass), set `role` to its name. The older `break_glass_role` field is deprecated.

```toml actions/db_migration.toml
name    = "db_migration"
timeout = "10m"
role    = "{{.nuon.install.id}}-migration-role"

[[triggers]]
type = "manual"

[[steps]]
name    = "run-migration"
command = "./migrate.sh"
```

## Set app-wide rules

Create `operation_roles.toml` at the root of your app config. Its rules apply across all installs and match on principal
(the entity running the operation) and operation:

```toml operation_roles.toml
type = "matrix"

[[rules]]
principal = "nuon::component:my_lambda"
operation = "deploy"
role      = "{{.nuon.install.id}}-lambda-deploy-role"

[[rules]]
principal = "nuon::component:my_lambda"
operation = "teardown"
role      = "{{.nuon.install.id}}-lambda-teardown-role"

[[rules]]
principal = "nuon::sandbox"
operation = "provision"
role      = "{{.nuon.install.id}}-provision-role"

[[rules]]
principal = "nuon::sandbox"
operation = "deprovision"
role      = "{{.nuon.install.id}}-destroy-role"

[[rules]]
principal = "nuon::action:db_migration"
operation = "trigger"
role      = "{{.nuon.install.id}}-migration-role"
```

### Principals

| Entity             | Principal                |
| ------------------ | ------------------------ |
| Specific component | `nuon::component:<name>` |
| All components     | `nuon::component:*`      |
| Sandbox            | `nuon::sandbox`          |
| Specific action    | `nuon::action:<name>`    |
| All actions        | `nuon::action:*`         |

Use `*` to set one role for every component or every action.

Each rule's `operation` is `provision`, `reprovision`, or `deprovision` for the sandbox, `deploy` or `teardown` for a
component, and `trigger` for an action run.

## Ship the config

After adding or changing operation role config, commit it and push to the git branch your
[app branch](/guides/app-branches) tracks:

```sh
git commit -am "update operation roles"
git push origin main
```

The push starts a branch run, which uploads your app config to the control plane.

## Check which role an entity uses

Open your install's **Components** or **Actions** tab in the dashboard. Each entity shows the
currently configured role.

## Override the role for one run

You can pick a different role for a single run without changing any config.

### CLI

Pass `--role-name` to `nuon actions create-run` and `nuon installs components deploy-all`. Pass `--role` to sandbox
runs, reprovisions, deprovisions, and teardowns:

```sh
nuon actions create-run -i <install-id-or-name> -w <action-id-or-name> --role-name my-custom-role
```

### Dashboard

On the install page, before triggering a run, use the role selector in the run options panel to choose a role from the install's
stack.

## Which role a run uses

When a role is set in more than one place, Nuon uses the first match in this order:

| Order | Where the role is set |
| --- | --- |
| 1 | Picked for a single run in the dashboard or command line |
| 2 | The sandbox, component, or action config |
| 3 | A rule in `operation_roles.toml` |
| 4 | The standard role for the operation |

If the matching role is switched off in your customer's stack, a role picked for a single run fails. Any other run uses
the standard role.
