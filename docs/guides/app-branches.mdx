This guide walks through setting up an [app branch](/concepts/app-branches) on an existing app template: writing the branch
config, sorting your installs into deployment groups, triggering runs, and approving
them.

## Prerequisites

- An [app template](/concepts/apps) created in Nuon with `nuon apps create`, and its app config committed to a GitHub
  repository.
- The [Nuon CLI](/cli) installed and authenticated (`nuon auth login`).
- For pull request previews, the **Nuon GitHub App connected in your org for the repository's owner**. See
  [connecting a repository](/guides/vcs).

<Note>
  Every branch of a given app must point at the same repository, and an install can belong to only one branch at a
  time. See [rules and limits](/concepts/app-branches#rules-and-limits) before you plan more than one branch.
</Note>

## Write a branch config

Add a file to a `branches/` directory in your app config directory, next to `metadata.toml`, one file per app branch.
It declares the branch name, the repo and git branch to track, and the deployment groups the rollout moves through.

```toml branches/main.toml
name = "main"

[connected_repo]
repo      = "acmeco/my-app-config"
directory = "."
branch    = "main"

[[install_groups]]
name  = "staging"
order = 1
[install_groups.label_selector]
env = "staging"

[[install_groups]]
name  = "production"
order = 2
[install_groups.label_selector]
env = "prod"
```

Three things to get right:

- **The repo block.** Use `[connected_repo]` for a repository connected through the Nuon GitHub App, or
  `[public_repo]` for a public one. Exactly one of the two, and `repo`, `directory`, and `branch` are all required.
  `directory` is the path to your app config within the repo, or `"."` if it is at the root. It can be any
  directory, with any name.
- **`name`** is the branch's name in Nuon. It comes from this key, and the filename has no effect on it. Commands that
  take `--branch-id` accept this name.
- **Group order.** `order` decides which group deploys first, lowest first. List your groups in the order you want
  them to run.

<Note>
  Every branch needs one of `[connected_repo]` or `[public_repo]`: the repo block is what the deployment groups sync
  against.
</Note>

Branch runs skip the `branches/` directory when they read your app config, so the branch file can live in the same
repo and directory it points at. Every field is documented in the [branch config reference](/config-ref/branch).

Each [install config](/guides/install-configs) names the branch that owns the install, by name or ID. `app_branch` is
required:

```toml
name = "customer-acme"
app_branch = "main"
```

Changing `app_branch` moves the install and applies the branch's latest non-preview run.

### Control when the branch runs

Omit `[run]` to use the default `push` mode, which runs on every push and previews pull requests. To give a customer
its own release cadence while still tracking `main`, gate the branch with a tag prefix:

```toml
[run]
mode       = "on_tag"
tag_prefix = "foobar/"
```

Pushing `foobar/v0.0.1` runs the tagged commit only when that commit is on the tracked branch's history.

For a merge-driven cadence, require an exact pull request label:

```toml
[run]
mode         = "on_github_label"
github_label = "deploy-cadence-daily"
```

When the PR lands, Nuon looks up the PR associated with the new commit and runs if the label matches.
`on_github_label` requires `[connected_repo]`. The other modes are `push` and `manual_only`; manual triggers remain
available in every mode.

### Selecting installs for a group

Each group picks its installs one of two ways: a `label_selector`, or an explicit list (`install_ids` and
`install_names`, which may be combined; names resolve to IDs at sync time). A label selector cannot be combined with
an explicit list in the same group:

```toml
# Recommended: matches any install carrying all of these labels.
[[install_groups]]
name  = "production"
order = 2
[install_groups.label_selector]
env  = "prod"
tier = "enterprise"
```

```toml
# Explicit names, resolved to install IDs when you sync.
[[install_groups]]
name          = "pilot"
order         = 1
install_names = ["customer-acme"]
```

```toml
# Explicit IDs.
[[install_groups]]
name        = "pilot"
order       = 1
install_ids = ["inlbmky2fz8qvrxp3d7twahjc9"]
```

<Tip>
  Prefer `label_selector`: it re-evaluates on every run, so group membership follows your labels with no re-sync.
  Explicit `install_names` are resolved to IDs once, at sync time.
</Tip>

### One branch or several

Most apps need one branch, `branches/main.toml`, and the rest of this guide assumes that. To track several branches of
the same repo (a `staging` branch and a `main` branch, for example), add one file per branch under `branches/`. The
`name` key inside each file sets the branch name.

Older app configs may have a single `branch.toml` at the root of the config directory. `nuon branches sync` reads it
the same way. Keep one layout per config directory: the app config parser rejects a `branch.toml` and a `branches/`
directory side by side.

## Label your installs

A label selector only matches installs that actually carry the labels. Set them with the CLI:

```sh
nuon installs labels set --install-id customer-acme env=prod tier=enterprise
```

Labels are key/value pairs, passed as positional `key=value` arguments. To inspect or remove them:

```sh
nuon installs labels list --install-id customer-acme
nuon installs labels unset --install-id customer-acme tier
```

You can also confirm which installs a selector will match before you run anything:

```sh
nuon installs list --labels env=prod --labels tier=enterprise --limit 200
```

All labels passed to `--labels` must match, so this is the same AND semantics a group's `label_selector` uses. On a
fleet of more than 20 installs, pass `--limit` at least your install count to list every match.

<Tip>
  Prefer keeping labels in install config files (a `[labels]` table, one file per install) so they are reviewed like
  the rest of your config, and apply them with `nuon installs sync -a <app-id> -d installs/`. To start from an
  install that already exists, export it: `nuon installs generate-config -i <install-id> > installs/<name>.toml`.
</Tip>


## Sync the branch config

Select the app once, then sync the branch file to create the branch and its deployment groups:

```sh
nuon apps select                                      # no flags: pick the app from the list
nuon branches sync --file branches/main.toml --dry-run
nuon branches sync --file branches/main.toml
```

`--dry-run` prints the plan and changes nothing. Without it, the command shows the same plan and asks before applying
it. Pass `--confirm` to apply without the prompt, which a non-interactive shell such as CI requires.

You run this once to create the branch, and again whenever you edit a branch file. Branch runs never read the branch
files, so a change to `branches/main.toml` takes effect only when you sync it. Every other change to your app config
ships by pushing to the tracked branch.

To sync every branch at once, pass the directory:

```sh
nuon branches sync --file branches/
```

Directory mode also proposes deleting any config-managed branch that no longer has a file. Syncing a single file only
touches the branch it names. A branch created by hand with `nuon branches create` is managed manually, and
`nuon branches sync` refuses to take it over.

Confirm what Nuon now has:

```sh
nuon branches list
nuon branches get --branch-id main
```

`list` prints each branch's name and ID. `get` returns the full branch, deployment groups included. Both default to
the app you selected with `nuon apps select`. Pass `--app-id` to target another app.

## Trigger a run

Once the branch exists, any push to the tracked branch starts a run:

```sh
git commit -am "bump chart version"
git push origin main
```

Nuon receives the push, and the run appears in the dashboard and in `nuon branches runs`.

You do not have to wait for a push. `nuon branches trigger` runs the tracked branch's latest commit:

```sh
# Runs against the tracked branch's latest commit.
nuon branches trigger --branch-id main

# Rebuild every component, including ones whose config did not change.
nuon branches trigger --branch-id main --force
```

A run builds a component when its config changed since the last run. If you changed only a component's source files
and left its config alone, use `--force` so the run rebuilds it.

Anything that can run the CLI or call the API can start the same run, which is how a CI job drives a rollout without
a webhook. The [GitHub Actions guide](/guides/github-actions) shows a workflow that triggers a run once your tests
pass.

`nuon branches trigger` and `nuon branches runs` open the full-screen workflow TUI, so you can watch steps and approve
from the terminal. Pass `--no-wait` to `trigger` to return as soon as the run starts. See the [TUI reference](/tui).

### Preview a change before you roll it out

To see what a change would do before it reaches the tracked branch, push it to another git branch and run a
plan-only preview against one install:

```sh
git push origin my-change
nuon branches preview --branch-id main --git-ref my-change --mode plan-only --install-id <install-id>
```

The preview builds the config from `my-change`, plans it against that install, and applies nothing. Use
`--pr-number` in place of `--git-ref` to preview an open pull request. Run `nuon branches preview` with no flags to
pick the branch, source, mode, and install interactively. A `[preview]` block in the branch file sets the default
mode and install, so the command can omit them.

## Approve or skip a deployment group

A run pauses at each group's plan step until someone acts on it. In the dashboard, open the app's **Branches** view,
then the run, and you will see the **Deployment plan** with each group's steps.

For each group:

- **Approve install group plan** — read the per-install diff, then approve to let the group's deploy step run.
- **Skip install group** — move the rollout past this group's deploy without applying it.

The run stops at the next group's plan step, so each group is approved or skipped on its own.

<Note>
  There is no setting that auto-approves a deployment group's plan. Each one needs a human in the dashboard or an API
  caller. If you want a machine to advance a rollout, subscribe to the [webhook](/guides/webhooks) events for the run
  and drive the approval through the API once your own checks pass.
</Note>

## Set up pull request previews

The one piece of setup is a **GitHub App connection in your org for the repository's owner**; the branch config
itself needs nothing. Opening a pull request against a tracked branch, or pushing another commit to an open one,
starts a plan-only run, and Nuon reports back on the pull request:

- a comment headed `## Nuon Preview — <BranchName>` (the branch's `name`, so usually `main`) with a table of config
  changes by section, edited in place on each later push rather than added to.
- a mode-specific commit status such as `nuon/<org>/<app>/<branch> preview (plan-only)`, linking to the preview run and moving from pending to
  success or failure.

If the pull request does not change the app config, the run stops early and the comment reports that the preview
was skipped.

Connect the GitHub App once, from [connecting a repository](/guides/vcs). After that, every branch tracking a repo
under that owner gets previews. The connection is an org-level setting, not a property of the branch config: a
`[public_repo]` branch pointing at `acmeco/my-app` gets previews just like a `[connected_repo]` one, provided your
org has connected `acmeco`.

<Note>
  Previews start posting as soon as your org has the GitHub App connection for the repository's owner. If they have
  not appeared yet, check that connection before you change the branch file.
</Note>

To run the same plan from the CLI before you open the pull request, push your git branch and use
[`nuon branches preview`](#preview-a-change-before-you-roll-it-out).

## Roll back a change

Every config change to an install is recorded as an app config version, and any earlier version can be applied again,
to one install or to a whole deployment group, with a plan in front of it. The
[rollback guide](/guides/rollback-install-config) walks through the exact calls.

## Command reference

| Command | What it does |
| --- | --- |
| `nuon branches sync --file <file-or-dir>` | Create or update branches from branch files. `--dry-run` prints the plan, `--confirm` skips the prompt. |
| `nuon branches list` | List the selected app's branches. Alias: `nuon br`. |
| `nuon branches get --branch-id <branch>` | Show a branch's details, including its deployment groups. |
| `nuon branches trigger --branch-id <branch>` | Run the tracked branch's latest commit. `--force` rebuilds everything, `--no-wait` skips the TUI. |
| `nuon branches preview` | Run a preview against a pushed git branch (`--git-ref`) or pull request (`--pr-number`). `--mode plan-only` applies nothing. |
| `nuon branches runs --branch-id <branch>` | List runs and open one in the workflow TUI. |
| `nuon branches create --name <name>` | Create a manually managed branch with no branch file. |
| `nuon branches delete --branch-id <branch> --confirm` | Delete a branch. |
| `nuon apps validate [dir]` | Check an app config directory before you push it. It looks up the app by the directory's name. |
| `nuon installs labels set --install-id <install> k=v ...` | Set labels used by group selectors. |
| `nuon installs labels list --install-id <install>` | List an install's labels. |
| `nuon installs labels unset --install-id <install> <key> ...` | Remove labels. |
| `nuon installs list --labels k=v` | Preview which installs a selector matches. |

Every `nuon branches` command defaults to the app selected with `nuon apps select` and takes `--app-id` to target
another. `nuon apps branches` still works as a deprecated alias.

## Migrating from `nuon apps sync`

`nuon apps sync` and `nuon sync` are deprecated: app config now ships through app branches. Once they are turned off
for your org, running `nuon apps sync` in an interactive terminal from your app config directory offers to migrate
you. The migration:

1. Reads the GitHub remote, the current git branch, and the config directory's path from your git checkout.
2. Writes `branches/<git-branch>.toml`, using `[connected_repo]` when your org has connected the repository and
   `[public_repo]` otherwise.
3. Syncs the new branch file, then offers to move your existing installs onto the branch.

Commit and push the new branch file to finish. To migrate by hand, write the branch file yourself and run
`nuon branches sync --file branches/<name>.toml`. Then move each install with `app_branch` in its install config, as
shown in [Write a branch config](#write-a-branch-config).

## Troubleshooting

**The branch synced but has no deployment groups.** The branch file is missing its `[connected_repo]` or
`[public_repo]` block. Add one and run `nuon branches sync` again.

**`nuon branches sync` says the branch is managed manually.** The branch was created with `nuon branches create` or in
the dashboard, and a branch file cannot take it over. Delete the branch, or give the file a different `name`.

**A push did not start a run.** Branch matching is on the exact repository and branch name. Check that the branch's
`branch` value matches the ref you pushed and that the repo is the one Nuon has connected. There are no path filters,
so a push that matches always starts a run. If nothing happened, the match itself failed.

**The pull request has no Nuon comment.** Your org has no GitHub App connection for that repository's owner. The
preview run itself succeeds and this is not reported as an error, so check the connection rather than the branch config.
Note this is about the *owner*, not the branch's repo block. A `[public_repo]` branch is fine if the owner is connected.

**A sync failed on an install name.** `install_names` must resolve to installs that exist in the org you are syncing
into. Switch the group to a `label_selector`, or create the install first.

**A group deployed to nothing.** No install carried the selector's labels. Check with
`nuon installs list --labels ...`.
