Container images allow you to import prebuilt container images from public sources, private AWS ECR repositories, private GCP Artifact Registry (GAR) repositories, and private Azure Container Registry (ACR) repositories.

Container images are used to import _prebuilt_ images, that have already been pushed to either a public registry, a private AWS ECR repository, a private GCP Artifact Registry repository, or a private Azure Container Registry repository.

<Note>
If you have private prebuilt images in a registry other than AWS ECR, GCP Artifact Registry, or Azure Container Registry, [please get in touch](https://nuon.co/contact-us)!
</Note>

To learn more about components, see the [Components](/concepts/components) concept page.

## Configuring a container image component

Private ECR, GAR, and credential-free ACR sources require a verified image-access [Cloud Connection](/guides/cloud-connections) in the same Nuon organization. Create the connection, apply its generated cloud setup, and verify it before saving or syncing your component configuration. Configure only the source image fields below; there is no user-supplied `cloud_connection_id`.

During configuration save or app sync, Nuon matches the platform and preset plus ECR account/region, GAR project/location, or ACR login hostname, and pins the unique resolved connection internally. Saving or syncing fails with setup guidance if no verified connection matches, or with conflict guidance if multiple verified connections match. Builds and metadata fetches use that connection while its identity, organization, target coordinates, and verified status remain valid. To use a replacement connection, save or sync again. **Repository names are not saved or used for matching; cloud IAM alone authorizes repository access.** See [how image connections are selected](/guides/cloud-connections#how-image-connections-are-selected) for exact matching rules and conflict resolution. Complete explicit ACR secret/certificate configurations remain supported as a separate mode.

### Using a Public Image

To use a public image from any container registry, configure the `public` block.

```toml components/public_image.toml
# container-image
name   = "public"
type   = "container_image"

[public]
image_url = "kennethreitz/httpbin"
tag       = "latest"
```

### Using a Private AWS ECR Image

To use an image from a private ECR registry, configure the `aws_ecr` block.

```toml components/ecr_image.toml
# container-image
name   = "ecr"
type   = "container_image"

[aws_ecr]
image_url = "123456789012.dkr.ecr.us-west-2.amazonaws.com/acme/api"
tag       = "latest"
region    = "us-west-2"
```

Use a unique verified AWS [Cloud Connection](/guides/cloud-connections) with the `ecr` preset belonging to the same Nuon organization. Nuon matches account `123456789012` and region `us-west-2`, not the repository name `acme/api`. [Configure its role for ECR read access](#aws-ecr-access-iam-role). Direct `iam_role_arn` configuration is rejected; existing ECR components must migrate before their next build or metadata fetch.

### Using a Private GCP GAR Image

To use an image from a private Google Artifact Registry, configure the `gcp_gar` block.

```toml components/gar_image.toml
# container-image
name   = "gar"
type   = "container_image"

[gcp_gar]
image_url      = "us-central1-docker.pkg.dev/my-project/my-repo/my-image"
tag            = "latest"
region         = "us-central1"
gcp_project_id = "my-project"
```

Use a unique verified GCP [Cloud Connection](/guides/cloud-connections#use-connections-for-private-gar-images) with the `gar` preset in the same organization. Nuon matches project `my-project` and location `us-central1` in this example, not the GAR repository `my-repo` or image path `my-image`. To migrate, apply the generated federation setup, remove component-level `service_account_email` and `workload_identity_provider`, and save or sync again. The connection-specific OIDC flow works independently of the cloud hosting Nuon; the control plane's GCP identity is not a substitute for a connection.

### Using a Private Azure ACR Image

For ACR without component-level credentials, use a unique verified Azure [Cloud Connection](/guides/cloud-connections#use-connections-for-private-acr-images) with the `acr` preset in the same organization. Nuon matches the exact login hostname (`acmeimages.azurecr.io` here), not the repository (`acme/api`).

```toml components/acr_image.toml
# container-image
name   = "acr"
type   = "container_image"

[azure_acr]
image_url    = "acmeimages.azurecr.io/acme/api"
tag          = "latest"
registry_url = "acmeimages.azurecr.io"
```

The connection authenticates an existing Microsoft Entra application through Nuon's connection-specific OIDC subject. When repository inputs are supplied, generated Azure CLI and Terraform instructions grant **Container Registry Repository Reader** with ABAC conditions for those repositories. These inputs generate permissions only; Nuon does not store them. No client secret or certificate is needed. Follow the [access setup directions](#azure-acr-access).

<Note>
The connection-based flow requires an ABAC-enabled registry. Nuon does not change existing registry permission modes. Omit component-level tenant, client, secret, and certificate fields in this mode. Complete [explicit secret/certificate configurations](#existing-secretcertificate-configurations) remain supported separately. An ACR component without explicit credentials requires a matching connection; the control plane's Azure identity is not a substitute.
</Note>

<Note>
Source-registry credentials are used by Nuon's builds and metadata fetches. They never land
in a customer cloud account, and access is shared across all installs of the app template
rather than configured per install.
</Note>

## Verifying signed images

Container image components can require the resolved image digest to be signed by a trusted Sigstore keyless identity or Cosign public key. Verification happens before Nuon copies the image, and a failed verification fails the component build.

See [Verify Container Image Signatures](/guides/image-signature-verification) for keyless and key-based configuration, authority matching, and guidance on combining verification with OPA policies.

## Deployments

Container image components _cannot_ be deployed directly in a customer install. When an image is released, it will be _synced_
into the customer install and made available to other components via [variables](/guides/using-variables).

To deploy a Container image component, reference the image from a Helm component or Terraform component:

```toml components/eks_deployment.toml
# helm
name       = "eks_deployment"
type       = "helm_chart"
chart_name = "<your-app>"

[connected_repo]
repo      = "<your-app>"
directory = "components/helm-chart"
branch    = "main"

[values]
"env.IMAGE_TAG"        = "{{.nuon.components.app_image.image.tag}}"
"env.IMAGE_REPOSITORY" = "{{.nuon.components.app_image.image.repository.uri}}"
```

```toml components/ecs_service.toml
# terraform
name              = "ecs_service"
type              = "terraform_module"
terraform_version = "v1.6.3"

[connected_repo]
repo      = "<your-app>"
directory = "components/ecs-service"
branch    = "main"

[vars]
"image_tag"        = "{{.nuon.components.app_image.image.tag}}"
"image_repository" = "{{.nuon.components.app_image.image.repository.uri}}"
```

```toml components/eks_job.toml
# action
name      = "eks_job"
type      = "job"
image_url = "{{.nuon.components.app_image.image.repository.uri}}"
tag       = "{{.nuon.components.app_image.image.tag}}"
```

## Image Syncing

When a Container image component is released, Nuon will automatically sync the image into the end customer account. This
image is stored in a local registry that is provisioned in the customer account. OCI referrers and legacy Cosign digest tags are copied with the image so signatures, SBOMs, provenance, and other attestations remain available in the destination registry.

Nuon image syncing allows you to sync images into accounts, without worrying about cross account permissions, registry
authentication or publishing public images. Any `Dockerfile` in a repo can be built, and synced.

The sync process works by creating a 1-time authentication flow that grants the install runner access to pull the image
from the org data plane, and copy it into the local registry.

## Granting Nuon Access to Pull Images

Your **vendor cloud administrator** applies source-registry setup in the account or project containing your images. End customers do not need access to that registry, and setup is not repeated for every install. Creating a Cloud Connection does not provision cloud trust or grant permissions; apply its generated setup with an identity authorized to manage the relevant IAM resources and grants.

Pick the section matching your **source registry**, independently of the cloud hosting Nuon or your customer installs. See [who sets up image repository access](/guides/cloud-connections#who-sets-up-image-repository-access) and the provider-specific prerequisites before starting. Verification checks exact-connection federation and foreign-subject rejection, plus ECR token retrieval or ACR token exchange where applicable; it does not probe repositories. After verification, fetch component metadata and run a build with an existing private image to check current permissions and exercise manifest and layer downloads.

For all three registries, omitting repository inputs generates identity-only setup with **no broad repository grant**. To grant an existing connection access to another repository, open its dashboard detail page and use **Add repository access**. Enter friendly repository names and have the vendor administrator apply the generated additive, permissions-only commands, or update the cloud IaC managing those permissions. This preserves the existing identity and immutable organization/trust tuple; it does not recreate federation, create a connection, or update a saved allowlist. Nuon makes no automatic cloud writes. See [Grant access to another repository](/guides/cloud-connections#grant-access-to-another-repository) for provider-specific grants and API setup generation.

| Image registry | Customer deployment | Setup |
|---|---|---|
| AWS ECR | Any | [AWS ECR Access IAM Role](#aws-ecr-access-iam-role) |
| GCP Artifact Registry | Any | [GCP GAR Access](#gcp-gar-access) |
| Azure Container Registry | Any | [Azure ACR Access](#azure-acr-access) |

### AWS ECR Access IAM Role

1. [Create an AWS Cloud Connection](/guides/cloud-connections#use-connections-for-private-ecr-images) with **Image repository access** (`--preset ecr`). In the dashboard, select the AWS region. Optionally enter repository names such as `acme/api` to generate initial permissions; Nuon derives the ARNs from the account, region, and names. In the CLI, provide `--default-region` explicitly and use optional repeatable `--repository-arn` flags for exact repository ARNs in that account and region. Repository inputs are transient, not a saved allowlist.
2. Apply its generated AWS CLI, Terraform, or CloudFormation setup in the account containing your ECR repositories. It creates the OIDC provider and role; when repository inputs are supplied, it also attaches an exact-repository ECR read policy. `ecr:GetAuthorizationToken` requires `*`; repository reads and pulls are scoped to the supplied ARNs. The policy grants no push or delete access. Reuse or import an existing OIDC provider rather than creating a duplicate.
3. Verify the connection, then save or sync the component with its source image URL, tag, and matching region. Nuon resolves and pins the unique verified AWS `ecr` connection from the account and region, not the repository ARN.

The generated trust policy binds the role to the exact Nuon OIDC subject `org:<org_id>:connection:<connection_id>` and audience `sts.amazonaws.com`. This works independently of the cloud hosting your Nuon control plane. When migrating an existing role, replace its previous trust configuration with the generated policy.

The ECR preset verifies role identity and exact trust, rejects a foreign connection subject, and retrieves an authorization token. It does not probe repository APIs or pull an image. Actual metadata fetches and builds check image access using current AWS permissions. A `custom` or `stacks` connection does not auto-match, even if its role has equivalent ECR permissions; use the `ecr` preset. Tag resolution with `update_policy` requires `ecr:ListImages`.

Nuon checks the saved identity, organization ownership, verified status, and matching account/region both when saving or syncing configuration and when executing builds or fetching metadata. Deleting the pinned connection or changing it to an unverified state prevents subsequent ECR use, including previously saved build plans. Fix its cloud setup and verify it again, or set up and verify a replacement and save or sync again; execution does not silently select a different connection.

### GCP GAR Access

1. [Create a GCP Cloud Connection](/guides/cloud-connections#use-connections-for-private-gar-images) with **Image repository access** (`--platform gcp --preset gar`). Enter the project ID and numeric project number. In the dashboard, enter the service account name and select a location such as `us-central1`. Optionally enter GAR repository IDs such as `api`, not image paths, to generate initial permissions. In the CLI, supply the service account email, provide `--default-region` explicitly, and optionally supply full resource names such as `projects/acme-project/locations/us-central1/repositories/api` using repeatable `--gar-repository` flags. Repository inputs are not stored.
2. Apply the generated **gcloud CLI** or **Terraform** instructions. They create a dedicated workload identity pool/OIDC provider and service account and bind impersonation to the exact Nuon connection subject. When repository inputs are supplied, they also grant `roles/artifactregistry.reader` on each selected repository. No project-wide reader, push, deletion, or service account keys are required.
3. Verify the connection, then save or sync the component with its source image URL, tag, project ID, and region. Nuon matches and pins the unique verified GCP `gar` connection using the project and location, not the GAR repository or image path.

The provider trusts Nuon's issuer, generated provider audience, and exact `org:<org_id>:connection:<connection_id>` subject. Uploaded public JWKS allow federation without a public discovery endpoint; refresh the provider's keys when the control-plane signing key rotates. When migrating, replace the previous service-account federation bindings with the generated binding.

Verification exchanges OIDC through GCP STS, impersonates the configured service account, and rejects a foreign connection subject. It does not read repository metadata or list images. Actual component metadata fetches and builds check current repository permissions, and builds exercise manifest and layer pulls.

The connection must retain its saved identity, belong to the same organization, match the source project/location, and remain verified and undeleted. This applies to configuration, app sync, metadata fetches, and builds, including previously saved builds. If you use `nuonco/gar-access/google`, migrate its federation setup to the generated connection setup before the next GAR build.

See the full set of `gcp_gar` fields in the [container-image config reference](/config-ref/container-image#gcp_gar).

### Azure ACR Access

1. Complete the [Azure vendor prerequisites](/guides/cloud-connections#azure-vendor-prerequisites): have an ABAC-enabled registry and create or choose a dedicated Microsoft Entra application and service principal in its tenant. Record the subscription ID, application client ID, tenant ID, registry resource ID, and login server. A new registry is only needed if no suitable ABAC registry is available; do not switch an existing registry's mode without planning its migration.
2. [Create an Azure Cloud Connection](/guides/cloud-connections#use-connections-for-private-acr-images) with **Image repository access**. In the dashboard, enter the subscription, tenant, and application client IDs, resource group, registry name, and actual login server. Optionally enter exact repository names to generate initial permissions. Nuon derives the registry ARM resource ID. The CLI uses `--platform azure --preset acr` and requires the full ARM resource ID with `--azure-registry-id`, along with the subscription, tenant, application client ID, and login server. Repeatable `--acr-repository` flags are optional transient setup inputs, not saved scope.
3. Apply its generated **Azure CLI** or **Terraform** instructions to add exact-subject OIDC federation and, when repository inputs are supplied, a repository-conditioned **Container Registry Repository Reader** grant. The registry must already use **RBAC Registry + ABAC Repository Permissions**. Changing an existing registry's mode requires a separate migration; Nuon does not do it.
4. Verify the connection, then save or sync the component with its source image URL, registry login hostname, and tag. Nuon matches and pins the unique verified Azure `acr` connection using the exact hostname, not the repository. Do not include component-level tenant, client, secret, or certificate fields in this mode.

The control plane's public OIDC discovery and JWKS endpoints must be reachable by Microsoft Entra. Verification checks the configured application's exact-connection authentication, foreign-subject rejection, and ACR token exchange, not repository reads. Actual metadata fetches and builds check current permissions, and builds exercise manifest and layer access. The connection must retain its saved identity, remain verified, belong to the component's organization, and match the source registry. Nuon obtains short-lived credentials when executing image operations.

#### Existing secret/certificate configurations

Complete explicit Azure secret/certificate configurations remain supported. For an RBAC-only registry, a service principal can still use registry-scoped `AcrPull` and an app secret or certificate. This is a different, broader access model from the new repository-scoped preset. To migrate, configure and verify a matching connection first, remove the component-level tenant, client, secret, and certificate fields, then save or sync again. Omitting these fields requires a matching connection.

<Note>
Only your build needs this. The install runner that deploys into a
customer's cloud account pulls the image from Nuon's own registry, never
from your ACR — so no access needs to be granted to any customer's Azure
identity. One service principal, scoped to your tenant, covers every install
of the app.
</Note>

**1. Create the app registration and service principal:**

```bash
az ad app create --display-name "nuon-acr-pull"
# note the "appId" field from the output — this is your client_id

az ad sp create --id <app-id>
```

**2. Grant `AcrPull`, scoped to just this registry:**

```bash
az role assignment create \
  --assignee <app-id> \
  --role AcrPull \
  --scope $(az acr show --name vendoracr --query id --output tsv)
```

**3. Create a credential.** Use a client secret, or a client certificate
(the better practice of the two, since it needs no plaintext secret at
rest):

```bash
# Option A: client secret
az ad app credential reset \
  --id <app-id> \
  --display-name "nuon-acr-pull-secret" \
  --years 1
# outputs a JSON object with "password" — this is the secret value
```

```bash
# Option B: client certificate
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout acr-pull.key -out acr-pull.crt -subj "/CN=nuon-acr-pull"

az ad app credential reset --id <app-id> --cert @acr-pull.crt --append

# Nuon needs the private key too, so bundle both into one PEM and base64
# encode it before storing it as an app secret
cat acr-pull.key acr-pull.crt | base64 > acr-pull-bundle.b64
```

**4. Store the value as an app secret**, never in app config or git:

```bash
# for a client secret
nuon apps variables create \
  --app-id <your-nuon-app-id> \
  --name acr_pull_secret \
  --value "<password-from-step-3>"

# for a client certificate
nuon apps variables create \
  --app-id <your-nuon-app-id> \
  --name acr_pull_cert \
  --value "$(cat acr-pull-bundle.b64)"
```

**5. Reference the secret by name** in the component's `azure_acr` block.
Set `tenant_id` to your tenant, `client_id` to the `appId` from step 1, and
`client_secret_name` or `client_certificate_name` (never both) to the app
secret name from step 4.

<Note>
Rotating the credential is a plain app secret update — run `nuon apps
variables create` again with the same `--name` to overwrite it. Nothing
re-runs automatically, so a stale or expired credential surfaces as a build
failure the next time the component builds, not immediately at rotation
time.
</Note>

See the full set of `azure_acr` fields in the [container-image config
reference](/config-ref/container-image#azure_acr).

## Importing Images Outside of Supported Registries

We currently support public container images, private AWS ECR repositories, private GCP Artifact Registry repositories, and private Azure Container Registry repositories.

If your registry is supported by AWS ECR's [pull through
  cache](https://docs.aws.amazon.com/AmazonECR/latest/userguide/pull-through-cache-working.html), the easiest way to
  import the images into Nuon is to setup a pull through cache and configure your container image to use it.

This works for [Docker Hub](https://hub.docker.com/), [Github Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) and [Microsoft Azure Container Registry](https://azure.microsoft.com/en-us/products/container-registry).

<Note>
If you would like to use a different private container registry, we would love to know more. Please [get in touch](https://nuon.co/contact-us) to tell us more about your use case.
</Note>
