## Toggleable components

Some components are optional: a customer on one tier gets observability, another doesn't; one install needs a certificate, another brings its own. **Toggleable components** let each install decide which components are enabled — without forking your app config.

Mark a component toggleable in your app config, with an optional `default_enabled` starting state:

```toml components/observability.toml
name            = "observability"
type            = "helm_chart"
toggleable      = true
default_enabled = false
```

A component's enabled state is stored as an [install input](/guides/configuring-inputs-and-secrets), and that input is the source of truth — the install config, the dashboard, and the CLI all write the same value. For config-managed installs, set the state per component in a `[component_toggles]` section:

```toml install.toml
name = "customer-acme"

[component_toggles]
observability = true
certificate   = false
```

When you run `nuon installs sync`, Nuon reconciles every toggle in a single pass: newly enabled components are deployed and newly disabled ones are torn down, all within one workflow. Enabling or disabling a component also runs its `pre`/`post` [lifecycle actions](/guides/actions) when defined.

### Inconsistent states are rejected up front

Toggle state has to stay consistent with the [component dependency graph](/guides/component-dependencies). Before applying any change, Nuon validates two rules:

- An enabled component cannot depend on a disabled one.
- A component cannot be disabled while an enabled component still depends on it.

These run **before** anything is deployed or torn down, so an inconsistent config is rejected rather than cascading into a half-broken install. Both declared `dependencies` and implicit output references (`{{.nuon.components.<name>.outputs...}}`) count as edges. For example, syncing a config that enables `api_gateway` while its `certificate` dependency is disabled fails with:

```
component "api_gateway" is enabled but its dependency "certificate" is disabled
  Enable "certificate", or disable "api_gateway", so the install reaches a consistent state.
```

You can also toggle a single component imperatively from the dashboard or CLI:

```bash
nuon installs components toggle --install-id <install-id> --component-id <component> --enable
nuon installs components toggle --install-id <install-id> --component-id <component> --disable
```

See the [Toggleable Components guide](/guides/toggleable-components) for the full reference.

## Kubernetes contexts

You can now bind a component to a cluster produced by a **peer component** through a named **Kubernetes context**. Define a context that points at a `terraform_module` or `pulumi` component exposing a `cluster` output, then have other components opt into it by name:

```toml metadata.toml
[[kubernetes_context]]
name      = "data-cluster"
component = "data-eks"
```

This decouples *where* a component deploys from *how* its cluster is provisioned, so several components can target different clusters defined elsewhere in the same app. See the [Kubernetes contexts reference](/config-ref/kubernetes-contexts).

## YAML and HCL inputs

[Inputs](/config-ref/inputs) now support `yaml` and `hcl` types in addition to `string`, `number`, `list`, `json`, and `bool`. Nuon validates the value's syntax when it's set, so a malformed Helm values block or `tfvars` snippet is caught at configuration time instead of mid-deploy.

```toml
[[inputs]]
name = "helm_values"
type = "yaml"

[[inputs]]
name = "network"
type = "hcl"
```
