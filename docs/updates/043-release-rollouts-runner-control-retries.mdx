## Release-driven rollouts

Ship to customers on your release cadence, not on every commit.

- Start an app branch run on a tag, on a merged pull request's label, or only manually
- Trigger a run for a specific tag, commit, or pull request from the CLI
- Trigger runs and previews from GitHub Actions with the Nuon action
- Every mode still rolls out through your install groups, with a plan and approval at each step

```toml branches/monthly.toml
[run]
mode       = "on_tag"
tag_prefix = "release/"
```

```sh
nuon branches trigger --branch-id main --run-type tag --run-ref v1.2.3
```

## Runner and stack control per install

Match each customer's AMI and CloudFormation requirements without forking your app.

- Pin the runner to a known-good AMI, or pick up the latest AL2023 AMI at every launch
- Override the runner image for a single install in `[stack_overrides]`
- Set root and nested CloudFormation parameters per install from its Git config
- Parameter changes queue a stack reprovision on their own

```toml runner.toml
image_auto_update = true
```

```toml installs/acme-production.toml
name             = "acme-production"
app_branch       = "main"
cloud_connection = "acme-aws"

[cloudformation.nested_stacks.VPC.parameters]
VpcCIDR = "10.42.0.0/16"

[cloudformation.nested_stacks.RunnerAutoScalingGroup.parameters]
InstanceType = "m7i.large"
```

## Safe retries for automation

Retry a timed-out call and get the original workflow back.

- Pass a `request_id` when you deploy, reprovision, or run an action or runbook through the API
- The same id and body return the original workflow instead of starting a second one
- The CLI takes `--request-id` on deploys, builds, branch triggers, and action runs
- `nuon actions create-run --wait` streams output and exits non-zero on failure or timeout
- Timed-out actions now report `timed-out`

```sh
nuon actions create-run -i customer1 -w pg_status \
  --env DEBUG=true --request-id pg-status-2026-10-22 --wait
```
