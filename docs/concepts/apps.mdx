An App Template is a series of TOML files that describe how your app is structured and what it depends on.
Each [install](/concepts/installs) is one deployment of an App Template.

## What's in a template

A template is a directory of TOML files in your own git repo. The [configuration reference](/config-ref) covers
each file.

```
my-app/
├── metadata.toml   # name and README
├── sandbox.toml    # VPC, cluster
├── inputs.toml     # customer values
├── secrets.toml    # customer credentials
├── policies.toml   # policy checks
├── components/     # your product
├── actions/        # scripts
└── runbooks/       # procedures
```

| Part | What it defines |
| --- | --- |
| [Sandbox](/concepts/sandboxes) | The base infrastructure every install gets, such as a network and a Kubernetes cluster. It can also reuse infrastructure the customer already has. |
| [Components](/concepts/components) | Your product. Each component wraps an existing Helm chart, Terraform module, Kubernetes manifest, or container image. Components can depend on each other and share outputs. |
| [Inputs](/concepts/app-inputs) | The knobs each customer sets for their install, such as region, instance size, or domain. |
| [Secrets](/concepts/app-secrets) | Credentials and API keys each customer supplies. |
| [Policies](/concepts/policies) | Checks that run before a build or deploy, written in OPA Rego or Kyverno. |
| [Actions](/concepts/actions) and [runbooks](/guides/runbooks) | Scripts and procedures you run against installs after they ship. |

## One product, several templates

Most teams create a few templates to offer different flavors of BYOC, such as an AWS and an Azure version, or one that
creates a new VPC and one that deploys into the customer's existing VPC.

## How a template changes

The template lives in git, so a change is a push. An [app branch](/concepts/app-branches) tracks a git branch of your
app config: each push builds what changed and rolls it out to your installs. Check your config with
`nuon apps validate` before you push.
