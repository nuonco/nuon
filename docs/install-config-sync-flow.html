Install Config Sync Flow

How install configs are synced from git, tracked per-install, and shown in the dashboard

1. Trigger Sources

Three ways an install config sync can be triggered. All use the same install-config-sync signal.

🔗
VCS Push (different repo)
GitHub webhook fires on the installs repo. github_event signal matches the installs VCS config and dispatches install-config-sync with changed files list.
🔀
App Branch Run (same repo)
Installs directory is in the same repo as the app config. The branch run workflow includes a "sync install configs" step after "fetch app config".
👆
Manual Trigger
User clicks "Sync now" in the dashboard or calls the API. Can sync all installs or a single install by name. Uses latest commit.

2. Data Model

Two new models track sync events and per-install changes. InstallConfigSync is one per sync event (commit/trigger). InstallConfigVersion is one per changed install.

AppBranchConfig |-- installs_directory # "installs/" (default) |-- installs_connected_github_vcs # optional: different repo for installs |-- installs_public_git_vcs # optional: public repo for installs InstallConfigSync # one per sync event (commit or manual trigger) |-- app_branch_id |-- app_branch_run_id # non-nil when part of a branch run |-- vcs_connection_commit_id # links to the commit |-- triggered_by # "vcs-push" | "manual" | "app-branch-run" |-- status # pending -> running -> success/failed |-- workflow_id # internal workflow (not shown in UI) `--> InstallConfigVersion[] # one per changed install |-- install_id |-- install_name |-- file_path # "installs/customer-acme.toml" |-- created # true = new install, false = update |-- diff # blob: JSON diff of what changed `-- status

3. VCS Push Flow (Different Repo)

When the installs repo is separate from the app config repo, VCS events route directly to the install-config-sync signal.

webhook GitHub Push Event
Push to myorg/my-installs repo on main branch. Payload includes commits[].added/modified/removed file paths.
signal github_event
Parses push payload. Extracts changed files list. Calls FindMatchingAppBranches which now also matches installs_connected_github_vcs_configs (polymorphic value: installs_app_branch_configs).
vcs/signals/github_event/execute.go
activity FindMatchingAppBranches
Returns matches with MatchType: "installs-config". The event handler routes to install-config-sync instead of vcspush.
vcs/worker/activities/find_matching_app_branches.go
NEWsignal install-config-sync
Receives: app_branch_id, changed_files, commit_sha, triggered_by: "vcs-push"
Optionally: install_name (for single-install sync)
apps/signals/branches/installconfigsync/signal.go
↓
NEWrecord InstallConfigSync
Created at the start of execution. Status: pending → running. Links to commit SHA and app branch.
activity Clone + Parse
1. Clone installs repo at commit SHA
2. Determine which files to process:
  • install_name set → {dir}/{install_name}.toml
  • changed_files set → filter to {dir}/*.toml
  • Neither → all *.toml in directory
3. Parse each TOML file into *config.Install
FOR EACH parsed install config
NEWactivity SyncInstallConfig
Calls dbSyncer.SyncInstall(ctx, installConfig)

Install not found? → Create via installs/helpers.CreateInstall
Install exists? → Compute diff via config.Install.Diff(), update if changed
apps/signals/branches/activities/sync_install_config.go
↓
NEWrecord InstallConfigVersion
Created per changed install. Stores:
• install_id, install_name, file_path
• created: true/false (new vs update)
• diff blob (JSON diff of changes)
• Links back to parent InstallConfigSync
record InstallConfigSync → success
Update status to success. Record synced_installs and failed_installs counts.

4. Same-Repo Flow (Part of App Branch Run)

When installs are in the same repo as the app config, the sync happens as a workflow step inside the branch run.

App Branch Run Workflow
Existing steps: fetch commit → fetch app config → sync install configs (NEW) → build components → deploy install groups
apps/workflows/app_branch_run.go
NEW Step: "sync install configs"
Dispatches the same install-config-sync signal with:
• triggered_by: "app-branch-run"
• app_branch_run_id: runID
• Skippable — no-op if no installs directory configured

The resulting InstallConfigSync links back to the AppBranchRun.
Continue with builds + deploys
Install configs are synced before builds start. New installs created here will be picked up by the install group resolution (label selectors or explicit IDs).

5. Manual Trigger Flow

User triggers sync from the dashboard or API. Same signal, different triggered_by.

Dashboard: "Sync now" button
All installs: POST /v1/apps/:appId/branches/:branchId/sync-install-configs
Single install: POST /v1/apps/:appId/branches/:branchId/sync-install-config with { install_name: "customer-acme" }
signal install-config-sync
triggered_by: "manual"
install_name: "customer-acme" (optional — if set, only syncs that install)
Uses latest commit on the configured branch.
Same execution as VCS push flow
Clone → parse → sync → create InstallConfigSync + InstallConfigVersion records.

6. DB Syncer Architecture

The existing Syncer interface gets a new SyncInstall method, separate from the app config Sync.

sync.Syncer interface |-- Sync(ctx) # existing: syncs app config (components, sandbox, etc.) |-- SyncInstall(ctx, install) # NEW: syncs a single install config |-- GetAppConfigID() # existing `-- ... # existing getters syncer.SyncInstall(ctx, *config.Install) → *InstallSyncResult 1. Look up install by name + app_id 2. Not found → installs/helpers.CreateInstall() • Sets managed_by: "nuon/git/install-config" • Creates with inputs, labels, cloud account, config, component toggles 3. Found → config.Install.Diff() • Update inputs, config, labels if changed 4. Return InstallSyncResult { InstallID, Created, Changed, Diff }

7. Example: Install Config TOML

Same format as nuon installs sync already accepts. Lives in the installs directory (e.g. installs/customer-acme.toml).

# installs/customer-acme.toml name = "customer-acme" approval_option = "approve-all" [labels] env = "production" tier = "enterprise" region = "us-east-1" [aws_account] region = "us-east-1" [[inputs]] api_key = "sk-xxx" domain = "acme.example.com" replicas = "3" [stack_overrides] vpc_nested_template_url = "https://nuon-artifacts.s3.us-west-2.amazonaws.com/templates/custom-vpc.yaml" [component_toggles] monitoring = true debug-tools = false [components.my-helm-chart] helm_values = """ replicaCount: 3 image: tag: v2.1.0 """

8. Example: Branch Config with Separate Installs Repo

The branch config declares two VCS connections: one for the app config, one for installs.

# Branch config (via API/dashboard) { "connected_github_vcs_config": { "repo": "myorg/my-app", "branch": "main" }, "installs_connected_github_vcs_config": { "repo": "myorg/my-installs", "branch": "main" }, "installs_directory": "installs/", "install_groups": [...] }
