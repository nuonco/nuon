Install / app-branch ownership model changes

Branch configs used to list which installs belong to a deployment group. Now each install declares its own branch and group, and the branch config only describes the groups themselves. Ownership moved off the installs table and onto an append-only connection ledger.

The lib/pq import went away with InstallIDs, and config validation changed from “label_selector is mutually exclusive with install_ids” to three rules: group names must be unique, every group needs exactly one of default or label_selector, and at most one group per branch may be the default.

Entity relationships

InstallAppBranchConnection is the source of truth. Moving an install deactivates the current row and appends a new one, so the full ownership history is preserved rather than overwritten.

Group resolution precedence

How an install is placed into one of its branch’s groups, in order. Implemented by ResolveInstallGroup in internal/app/apps/helpers/install_branch_ownership.go.

First
source = explicit

The stored group is pinned and wins outright. Naming a group that does not exist on the branch is a user-facing error.

→
Then
group.LabelSelector

Match the install’s labels against each group’s selector. Matching more than one group is an error; an install can only belong to one group per branch.

→
Then
group.Default

The single group flagged default catches every remaining install the branch owns.

→
Otherwise
validation error

A branch assignment cannot be created or updated when no group resolves.

Migrations

Applied in order. The legacy installs.app_branch_id column is intentionally left in place, because installs_view_v9 selects i.* and dropping it requires a new view version.
