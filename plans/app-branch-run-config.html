App Branch Run Configuration

One trunk, many release cadences — all • on_tag_prefix • on_github_label • manual_only

01One trunk, many cadences

Every app branch below tracks the same git branch (main) in the same repo. The tracked branch says which product line the app branch is a cadence of. run.mode says when it runs and which commit it builds.

The key idea
Foobar sits on C while GA has already taken D and M. Same history, slower clock. The clone keys off the commit SHA, so a tag run builds the tagged commit — never the current tip of main.

Manual triggers (dashboard, CLI, MCP) are never gated by run.mode. “Manual only” means VCS will not start a run; an operator still can, at any commit — which is the hotfix and catch-up path for every cadence mode.

03Event routing

Today a tag push dies at the parser: github_event/parse.go rejects any ref that is not refs/heads/*. Candidate matching is repo + git branch in find_matching_app_branches.go. Both grow a tag path, then every matched branch passes through one gate.

Skip early, not late
A mode skip happens after matching and before a run row is created — the same shape as the existing draft-PR skip in trigger_app_branch_run_from_vcs_push.go. Never create a run and mark it not-attempted: at scale, one customer’s tag would leave a dead run on every other customer’s branch. That noise is the whole reason this gate exists on the app branch instead of the install group.

04Tag runs: prefix, then ancestry

Two independent checks. The name decides which app branch cares (strings.HasPrefix, case-sensitive, not a regex). The commit decides whether the tag is legitimate for that trunk.

Behind is fine. Tagging an older commit is the normal case for a customer catching up to an earlier release, so behind is accepted, not just identical. What gets rejected is history that is not on the trunk at all.

05Label runs happen at merge, via the API

A labeled PR against main still previews on the GA branch only. The cadence branch waits for the merge. The label lives on the pull request, and a squash or rebase merge payload carries none of it — so the push webhook cannot answer the question and we ask GitHub.

06Configuration

# customer cadence, driven by tags
[[branch]]
name = "foobar"

[branch.connected_repo]
repo      = "acme/app"
directory = "."
branch    = "main"   # same trunk as GA

[branch.run]
mode       = "on_tag_prefix"
tag_prefix = "foobar/"
# shared cadence, driven by PR labels
[[branch]]
name = "daily"

[branch.connected_repo]
repo      = "acme/app"
directory = "."
branch    = "main"

[branch.run]
mode         = "on_github_label"
github_label = "deploy-cadence-daily"

Stored as JSONB on AppBranchConfig, mirroring preview_config, so every config revision snapshots the rule it ran under. Omitting the run block means all — today’s behavior, unchanged for every existing branch. 

type AppBranchRunConfig struct {
    Mode        string `json:"mode"`                    // all | on_tag_prefix | on_github_label | manual_only
    TagPrefix   string `json:"tag_prefix,omitempty"`
    GithubLabel string `json:"github_label,omitempty"`
}

07Validation

RuleWhy
on_tag_prefix requires tag_prefixWithout it the mode would match every tag in the repo — the opposite of the intent.
on_github_label requires github_labelSame reason, and an empty label would match nothing rather than everything, which is harder to notice.
on_github_label requires connected_repoLabel lookup needs the GitHub App API. A public_repo branch has no credential to ask with.
Cross-field exclusiontag_prefix only with on_tag_prefix, github_label only with on_github_label. Reject rather than ignore, so the TOML cannot lie about what triggers a deploy.
Unknown mode fails the syncA typo like on_tag silently falling back to all would ship every commit to a customer that opted out.
Tag deletes ignoredDeleting foobar/v0.0.1 is not a release event.

09Footguns worth designing around

  • Tag on a commit that never landed. Tagging a hotfix branch will not update the customer until that commit reaches the tracked branch and a matching tag points at it. The skip must be logged loudly or it looks like a dropped webhook.
  • Label added after the merge. Nothing backfills. The run is decided at the moment of the push; a late label needs a manual run.
  • Label removed before the merge. Silently no deploy — the PR looks merged and done.
  • Cherry-picks associate multiple PRs with one commit. Any matching label counts.
  • Every cadence branch shares a trunk with GA. That is exactly why on_tag_prefix and on_github_label must skip PR previews; otherwise one PR fans out a preview to every customer branch in the repo.

10Out of scope for this slice

Called out in the tags plan, but not this change: branch-level component / stack / sandbox overrides, install-group staleness when groups advance at different times, and re-running a stale plan. This slice is only about whether and at which commit an app branch run starts.
