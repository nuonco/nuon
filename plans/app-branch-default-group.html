App Branch Default Install Group

One group per branch marked default = true — every install no other group claims lands there, until labels promote it out

01The gap this closes

You pick the app branch when you create an install — that is the one decision available up front. Group membership comes from labels, and labels usually arrive later: after the install provisions, after the customer is onboarded, after someone decides which tier it is. In between, the install belongs to a branch but matches no group, so every run of that branch skips it. Today the dashboard calls that state Orphaned. A default group turns that hole into a landing zone.

02Resolution: selectors first, default last

The default group is a pure fallback. It carries no label_selector, no install_ids, no all_installs — its membership is defined entirely by what the other groups did not take. Resolution runs per install, over the installs the branch already owns, and is recomputed on every run.

Why fallback rather than a wildcard selector
A group could already be written to catch everything with all_installs, but that collides with every other group the moment a label matches — an install would be in two groups, which is an error. “Everything nobody else took” is not expressible as a selector, so it is a flag, for the same reason all_installs is a flag rather than an empty selector.

03Configuring it — kitchen-sink, before and after

This is ~/nuon/kitchen-sink/branches/default.toml as it stands, then with staging converted into the branch’s default group. The change is a deletion plus one key: staging stops asking for env = "staging" and instead accepts whatever customers and enterprise do not claim.

Today

# branches/default.toml
name = "main"
post_deploy_runbooks = ["full-health-check"]

[public_repo]
repo      = "nuonco/kitchen-sink"
directory = "."
branch    = "jm/change-tests"

[run]
mode = "push"

[[install_groups]]
name  = "staging"
order = 1

[install_groups.label_selector]
env = "staging"          # must be labeled to land here

[[install_groups]]
name  = "customers"
order = 2

[install_groups.label_selector]
env  = "production"
tier = "customer"

[[install_groups]]
name  = "enterprise"
order = 3

[install_groups.label_selector]
env  = "production"
tier = "enterprise"

With a default group

# branches/default.toml
name = "main"
post_deploy_runbooks = ["full-health-check"]

[public_repo]
repo      = "nuonco/kitchen-sink"
directory = "."
branch    = "jm/change-tests"

[run]
mode = "push"

[[install_groups]]
name    = "staging"
order   = 1
default = true          # catches every unclaimed install

# no label_selector, no install_ids: membership is
# "whatever the groups below did not match"

[[install_groups]]
name  = "customers"
order = 2

[install_groups.label_selector]
env  = "production"
tier = "customer"

[[install_groups]]
name  = "enterprise"
order = 3

[install_groups.label_selector]
env  = "production"
tier = "enterprise"

Rejected at sync and at save

# A default group cannot also select.
[[install_groups]]
name    = "staging"
default = true
[install_groups.label_selector]
env = "staging"   # ← error

branch "main": install group "staging" is the
default group and cannot set label_selector,
install_ids, install_names, or all_installs

# Only one default per branch.
[[install_groups]]
name    = "staging"
default = true

[[install_groups]]
name    = "canary"
default = true   # ← error

branch "main": install groups "canary" and
"staging" are both marked default; a branch
has at most one default group

Omitting default everywhere is the existing behaviour, unchanged: unmatched installs stay orphaned and the dashboard keeps warning about them. Nothing about this is required to adopt.

04Marking the default in the deployment plan editor

Same modal as today (DeploymentPlanEditor), one new group-level control. It reads as a choice among groups, not a per-group checkbox — marking a new default clears the old one in place, so the plan can never be saved with two.

  • Marking a group default clears its targeting in the editor and swaps the Manual / Labels / All installs control for the fallback summary. Unmarking it restores an empty Manual group.
  • The live count under the default group is the same effective-membership calculation the plan view uses, so the editor and the plan never disagree.
  • A default group is the one group that may legitimately be empty. It is exempt from “a group can’t be saved empty”.

05Creating an install: the group step disappears

Today the flow is branch → details → pick a group, where the group picker exists to apply the labels that would make the install match something. On a branch with a default group, the picker has nothing to ask: the install already has a home, and labels — entered on the details step like any other label — decide whether it stays there.

The preview is a hint, not the decision
“Deploys with staging” on step 2 is computed client-side from the labels in the form against the branch’s current plan. The install is created with labels only — never with a group ID — and the server resolves membership at run time. If someone edits the plan between the preview and the run, the run is right and the preview was stale, which is the correct direction for that race.

06Presenting the plan

The default group renders as a group like any other, with a Default badge and the installs currently falling through to it. The Orphaned block only appears on branches with no default — with one configured, there is nothing left to orphan.

07Promotion out of the default

Nothing is “moved”. Labels change, the next resolution finds a non-default match, and the install deploys from that group instead — in that group’s order, with that group’s approval and auto-approve settings.

08Rules at a glance

Situation Behaviour
default = true
on one group		 Allowed. That group holds every install the branch owns that no other group matches.
default on two groups Rejected at config sync and at plan save. The editor makes it unreachable by treating default as a single choice across groups.
default + label_selector
or install_ids / all_installs		 Rejected. A default group is a pure fallback; mixing the two makes “which installs are here” unanswerable without precedence rules nobody asked for.
no default group Unchanged. Unmatched installs are orphaned and the plan keeps warning about them. Every existing branch keeps working untouched.
default group is empty Fine, and expected on a fully-labeled fleet. It is exempt from the “a group can’t be saved empty” rule and its run steps are a no-op.
install matches two
non-default groups		 Still an error. The default group is a fallback, not a tie-breaker — ambiguity between real selectors keeps failing loudly.
preview runs Unaffected. Preview targets come from preview.install_id / preview.label_selector and never consult install groups.
install moved to
another branch		 Resolution starts from branch-owned installs, so an install only ever falls into the default group of the branch that owns it.
Open question worth settling before build
Should the default group be allowed to carry auto_approve_on_policies_passing = true? It is the group that will contain installs nobody has classified yet, so auto-approving it is the most convenient setting and the easiest one to regret. Leaving it configurable (defaulting off) is the proposal here, but a hard block is defensible.
