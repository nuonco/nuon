Bundles

A bundle is cut 1:1 from an app-branch-run when the app has bundle_enabled: true. It packages every component build artifact, the sandbox build, and an encoded workflows manifest into a single OCI artifact with a manifest digest, transport checksum, and per-install ed25519 signatures.

Bundle installs

An install with management_mode: bundle has no Nuon-managed runner. The customer runs the installer, which pulls bundles, verifies them against the install's public key, shows an approval view, and executes the workflow steps locally — pushing back a limited set of status: bundle state, workflow statuses, component health.

Installer modes

  • remote installer-api proxies the control plane with a short-lived scoped token
  • local installer-api reads/writes everything from the customer's S3 bucket

Reused machinery

  • pkg/runner/controlplane/executor.go — embeddable job executor
  • RunnerJob.Executor gains third value installer
  • Existing WorkflowStepApproval / Response flow
  • pkg/runner/oci/archive oras packing, org ECR repos

Insertion point

The publish step group slots in after builds, before the preview early-return and install groups in the branch-run step generator. It is skippable, so a publish failure never blocks managed installs from deploying.

Storage

Primary artifact is an OCI index in the org's ECR registry (repo <org>/<app>/bundles, provisioned like component repos). A tar.gz export is produced on demand by the download-grant endpoint and served via a presigned URL — that one file is the manual handoff.

Auth model

bootstrap HMAC join secret proves agent identity at a public endpoint (precedent: stack phone-home). steady state ctl-api mints a short-lived token carrying the existing installer role scoped to the install (precedent: runner-auth token minting). Revoking the agent stops honoring its HMAC.

Signing & verification

Each install can create one active keypair (InstallSigningKey): private key server-held in Secrets Manager, public key exposed via API so the customer can pin it out-of-band. Publish signs the manifest digest per bundle-mode install; the installer's verify uses only the public key + new shared pkg/signing.

Local mode

With no control-plane connectivity, the installer-api reads bundles and records state (statuses, approvals) in the customer's S3 bucket, then replays pushes on reconnect. Same UI, same verify path.

No new dispatch system

The installer is, from the control plane's perspective, a runner: jobs carry Executor = installer, only the installer's token can claim them, and results flow through the existing execution-result endpoints — so workflow status appears in the dashboard with zero new ingestion code.

Structural prerequisite

Promote bins/runner/internal/jobs/{deploy,actions,sandbox,healthcheck} → pkg/runner/jobs/ so the embeddable executor can register deploy handlers. Mechanical move, shipped as its own PR.

Approvals

Reuses WorkflowStepApproval / WorkflowStepApprovalResponse and the conductor's 30-day await unchanged. Bundle installs default plan steps to execution type approval — the customer must approve in the installer UI before apply runs.

Managed install controls

For managed installs the same installer surface exposes read-only resources, health, and approvals — powered by the control-plane API with the scoped token (remote mode only).
