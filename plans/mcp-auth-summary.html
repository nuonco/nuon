1. Overview & the /livez fix

The jm/mcp-server branch adds a streamable-HTTP MCP server hosted inside ctl-api, listening on port 8088 at /mcp. It is a fifth HTTP server alongside public (8081), internal (8082), runner (8083), and auth (8084).

Bug found & fixed The dev orchestrator health-checks http://localhost:8088/livez, but the MCP server built a bare http.Server whose handler was only the MCP protocol handler — it never served /livez. So the probe never returned 200 and ctl-api sat in "Starting" forever, even though the MCP server was actually listening.
Fix Put an http.ServeMux in front: /livez and /readyz return 200, and / remains the catch-all for the MCP handler (so /mcp still routes through unchanged).
services/ctl-api/internal/app/mcp/server/server.go

Every other ctl-api server registers /livez, /readyz, /version via the shared health.Service (internal/health/health.go); the MCP server bypassed that machinery entirely.

2. Current MCP server auth

The MCP server authenticates with two HTTP headers on each request and is a pure token consumer — it never issues or persists tokens.

HeaderAuthorization: Bearer <token> — must match a non-expired row in the tokens table
HeaderX-Nuon-Org-ID: <org_id> — must be an org the token's account can access

Never persists tokens auth.go only reads the tokens table. The only in-memory state is a session map holding {OrgID, AccountID} — not the token. The only MCP tool DB writes are approve/reject step records. So the MCP surface can never create or store a credential.

3. Human auth — Path A: upstream OIDC JWT (dashboard)

Humans using the dashboard authenticate via an OAuth/OIDC flow against a configured upstream IdP. The resulting JWT is validated cryptographically on every ctl-api call (issuer, expiry, JWKS signature, email claim) using github.com/auth0/go-jwt-middleware. New accounts are auto-provisioned; the validated JWT is cached in the tokens table as TokenTypeAuth0.

4. Human auth — Path B: opaque token (CLI / static tokens)

API tokens are opaque strings looked up directly in the tokens table — no cryptographic validation, just a DB match + expiry check. This covers nuon auth login (device-flow) tokens, static service-account tokens, and Nuon Auth session cookies. This is the same mechanism the MCP server uses today.

The middleware tries both On each request ctl-api attempts the opaque lookup (Path B) first, then falls back to JWT validation (Path A).

5. Token issuance & storage

The branch added endpoints to mint a service account + static token for an app to call ctl-api. Each static token gets its own dedicated AccountTypeService account, scoped to one org, with a role (org_read_only default, or org_support / org_admin).

6. Proposed: OAuth for MCP (no CLI)

Goal: a user adds only a URL (https://ctl.nuon.co/mcp) in any agent and authenticates in the browser — no CLI install, no manual token handling. This makes the MCP server an OAuth 2.0 Resource Server and uses Nuon Auth as the Authorization Server (reusing existing upstream-IdP federation for the human login step).

sequenceDiagram
    autonumber
    participant A as Agent (any MCP client)
    participant M as MCP server (Resource Server)
    participant AS as Nuon Auth (Authorization Server)
    participant IdP as Upstream IdP
    participant U as User (browser)

    A->>M: MCP request (no token)
    M-->>A: 401 + WWW-Authenticate
(resource metadata URL)
    A->>M: GET /.well-known/oauth-protected-resource
    M-->>A: { authorization_server: Nuon Auth, resource }
    A->>AS: GET /.well-known/oauth-authorization-server
    AS-->>A: { authorize, token, registration endpoints }
    A->>AS: POST /register (Dynamic Client Registration)
    AS-->>A: client_id
    A->>AS: /authorize (PKCE + resource indicator)
    AS->>IdP: federate human login
    U->>IdP: authenticate
    IdP-->>AS: identity
    AS-->>A: authorization code
    A->>AS: POST /token (code + PKCE verifier)
    AS-->>A: access token (+ refresh)
    A->>M: MCP request + Bearer access token
    M->>M: validate token (audience-bound), resolve account + org
    M-->>A: MCP tools

ComponentAdd
MCP server

Nuon Auth

Does it mirror human auth?

Mostly yes The token-validation half mirrors the dashboard flow (Path A) exactly — same "OAuth against an IdP → validate token per request" model, and it can reuse saveAccountToken. Two pieces are genuinely new for MCP:
  • Dynamic Client Registration — humans use pre-registered clients (dashboard, CLI); agents must self-register.
  • Discovery + WWW-Authenticate — an agent bootstraps from just a URL; a human "knows" to open the dashboard.
And org selection is the one place human auth relies on a mechanism (the X-Nuon-Org-ID header) that has no MCP equivalent.

7. Key design decisions

DecisionRecommendationWhy
Org selection Per-org resource URLs: /mcp/{org_id} Org rides in the OAuth resource indicator (RFC 8707); token is audience-bound to one org. No header needed.
Token format Opaque (DB lookup), hashed at rest Matches existing model, instantly revocable, no JWKS needed. JWTs save a lookup but can't be cheaply revoked.
Client registration Dynamic Client Registration (RFC 7591), rate-limited Required for "any agent, no manual setup." Guard redirect URIs / rate-limit to avoid abuse.
Scopes Map to roles (org_read_only, org_admin) Gate which MCP tools are exposed (read tools vs. create_install / deploy_component).
AS choice Nuon Auth as AS (vs. upstream IdP directly) Upstream IdP may not support DCR + PKCE public clients + audience binding. Nuon Auth already issues tokens; wrap it in an OAuth AS interface.
Open question Whether you can point MCP resource metadata directly at the upstream IdP (max reuse, min code) or must insert Nuon Auth as the AS depends on what the configured upstream IdP supports (DCR, PKCE public clients, audience-bound tokens). Confirm the IdP's capabilities before committing to a path.
